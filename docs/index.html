Parallel agents are the easy part. Landing their work isn't. 병렬로 돌리는 건 어렵지 않습니다. 어려운 건 머지까지입니다.

Running agents side by side is the horizontal axis. Wooi adds the vertical one: dependent work branches off the work it depends on, and the whole chain stays valid as parents merge. Agents build those chains themselves through Wooi's built-in tools, and every review lands on the diff instead of in a transcript. 에이전트를 나란히 돌리는 건 가로축입니다. Wooi 는 세로축을 더합니다 — 이어지는 작업은 자기가 딛고 선 작업에서 분기하고, 부모가 병합돼도 체인 전체가 유효하게 남습니다. 그 체인은 에이전트가 내장 도구로 직접 쌓고, 리뷰는 읽고 마는 기록이 아니라 diff 위에 붙습니다.

Why Wooi왜 Wooi 인가

The bottleneck already moved 병목은 이미 옮겨갔습니다

Running agents in isolated worktrees is table stakes now — plenty of orchestrators already do it. But worktrees solve file collisions; they don't solve dependencies. The unsolved half is downstream: branches that were written in parallel and have to land in sequence, and a review queue that grows as fast as the agents write. Here's where Wooi puts its weight. 격리된 worktree 에서 에이전트를 돌리는 건 여러 오케스트레이터가 이미 지원합니다. 하지만 worktree 는 파일 충돌은 막아도 의존성은 못 풉니다. 안 풀린 쪽은 그 다음입니다. 병렬로 쓰였지만 순서대로 머지돼야 하는 브랜치들, 그리고 에이전트가 코드를 쓰는 속도만큼 쌓이는 리뷰 대기열. Wooi 가 힘을 싣는 자리가 여기입니다.

🧱

Stacked PRs are a first-class citizenStacked PR 이 1급 시민입니다

The whole app knows what a chain is, not just the branch you're standing on. Work that builds on other work branches off it instead of off the default branch. Restack rebases onto the latest parent; when a parent merges, a merge cascade retargets each child PR to the grandparent and rebases the children onto it; a PR that drifts onto the wrong base gets flagged instead of silently accepted. Build a chain by hand with git checkout -b and gh pr create and Wooi reconstructs the stack from the PRs' base links. 지금 서 있는 브랜치뿐 아니라 앱 전체가 "체인"을 압니다. 앞선 작업 위에서 이어지는 작업은 기본 브랜치가 아니라 그 작업의 브랜치에서 분기합니다. Restack 은 최신 부모 위로 rebase 하고, 부모가 병합되면 병합 캐스케이드가 자식 PR 의 base 를 조부모로 옮기고 자식들을 그 위로 rebase 합니다. base 가 어긋난 PR 은 조용히 받아들이는 대신 알려 줍니다. git checkout -b 와 gh pr create 로 손수 만든 체인도 PR 의 base 링크에서 복원해 똑같이 보여 줍니다.

🤖

Agents orchestrate the app, not just the repo에이전트가 리포가 아니라 앱을 조종합니다

Every session gets a built-in MCP server. check_related_work shows which files the other workspaces are touching before an agent starts, create_workspace / create_stacked_workspace split a task into a chain of reviewable PRs, and report_to_parent / notify_child carry results along that chain. It's fenced in: an agent can only target workspaces it created, and sibling paths are shared — never diffs. 모든 세션에 내장 MCP 서버가 붙습니다. check_related_work 로 다른 워크스페이스가 건드리는 파일을 시작하기 전에 확인하고, create_workspace·create_stacked_workspace 로 작업을 리뷰 가능한 PR 체인으로 쪼개며, report_to_parent·notify_child 로 결과를 체인을 따라 주고받습니다. 울타리도 있습니다 — 자기가 만든 워크스페이스만 겨냥할 수 있고, 형제와 공유되는 건 파일 경로뿐, diff 는 절대 넘기지 않습니다.

🔍

Review is a workspace, not a paragraph리뷰는 한 문단이 아니라 작업 공간입니다

Every agent can review a PR now; what's missing is somewhere to work the result. A Wooi review is its own entity with its own worktree. Findings are anchored to diff lines with a severity badge — edit, discard, post one or post the batch. Files carry a viewed mark that auto-clears when a new commit changes them, replies are polled so you can follow up, and verdicts are guarded. PR 리뷰는 이제 어떤 에이전트든 합니다. 없는 건 그 결과를 다룰 자리입니다. Wooi 의 리뷰는 전용 worktree 를 가진 독립 엔티티입니다. 지적은 심각도 배지와 함께 diff 줄에 앵커되고 — 고치고, 버리고, 낱개로든 한꺼번에든 게시합니다. 파일의 봤음 표시는 새 커밋이 그 파일을 바꾸면 저절로 풀리고, 답글은 주기적 으로 가져와 이어서 물어볼 수 있으며, 판정에는 가드가 있습니다.

🎛️

Two agent backends, integrated deeply두 백엔드를 얕지 않게

Claude Code and OpenAI Codex, each supported down to its own controls rather than reduced to a lowest common denominator: /rewind and /btw where the backend has them, per-backend permission modes, reasoning effort and fast mode, account rate limits normalized into one readable status line, and your own MCP servers inherited from your CLI config. Claude Code 와 OpenAI Codex 를 최소 공통분모로 깎는 대신 각자의 조작 방식까지 따라갑니다. 백엔드가 지원할 때의 /rewind·/btw, 백엔드별 권한 모드, reasoning effort 와 fast mode, 상태줄 하나로 정규화한 계정 레이트리밋, 그리고 사용자가 CLI 에 설정해 둔 MCP 서버 승계까지.

🔒

Quiet where it counts조용해야 할 곳에서 조용합니다

No telemetry and no servers of its own — settings and transcripts stay on your machine. Updates can wait for "restart when work finishes" instead of killing a running turn. Ignored-but-needed files like .env are carried into every new worktree, and sessions resume across restarts. 텔레메트리도, 자체 서버도 없습니다 — 설정과 대화 기록은 내 컴퓨터에만 남습니다. 업데이트는 돌아가는 턴을 끊는 대신 "작업이 다 끝나면 재시작" 을 기다릴 수 있고, .env 처럼 git 이 추적하지 않지만 꼭 필요한 파일은 새 worktree 마다 전달됩니다. 세션은 앱을 껐다 켜도 복원됩니다.

How it works동작 방식

Repository → Workspace → PR리포 → 워크스페이스 → PR

One task = one dedicated git worktree + branch + agent session. Nothing runs until you send your first message. 작업 1개 = 전용 git worktree + 브랜치 + 에이전트 세션 1개. 첫 메시지를 보내기 전까지 아무것도 실행되지 않습니다.

01

Connect a repo리포 연결

Point Wooi at a git repository (its main checkout). Configure per-repo Setup / Dev / Archive scripts like npm install. git 리포(메인 체크아웃)를 연결합니다. 리포 단위로 Setup / Dev / Archive 스크립트(npm install 등)를 지정합니다.

02

Spin up a workspace워크스페이스 생성

Each task gets its own worktree + branch + agent session under ~/wooi/workspaces/<repo>/<branch>, running independently and in parallel. 작업마다 전용 worktree + 브랜치 + 세션이 ~/wooi/workspaces/<repo>/<branch> 에 생성되어 독립적·병렬로 실행됩니다.

03

Land the work머지까지

Open a GitHub PR in one click. If the task builds on another, stack it and Wooi keeps the chain rebased and retargeted as parents merge — and review lands on the diff, not in a chat log. 클릭 한 번으로 GitHub PR 을 엽니다. 앞선 작업 위에 얹히는 작업이면 스택으로 쌓아 두면, 부모가 병합될 때마다 Wooi 가 체인을 rebase 하고 base 를 옮깁니다. 리뷰는 채팅 로그가 아니라 diff 위에 붙습니다.

Agent support: Since v1.4.0, Wooi supports both Claude Code and OpenAI Codex. Choose an agent when you create a workspace; models, reasoning effort, permissions, and commands adapt to that backend. 에이전트 지원: v1.4.0부터 Claude Code와 OpenAI Codex를 모두 지원합니다. 워크스페이스를 만들 때 에이전트를 선택하면 모델·reasoning effort·권한·명령이 해당 백엔드에 맞게 표시됩니다.
Features기능

Everything you need to run agents in parallel — and land what they write에이전트를 병렬로 돌리고, 그 결과를 머지하기까지

🧱

Stacked PRsStacked PR

  • No extra tooling추가 도구 없음 — not every task is independent — sometimes step 2 builds on step 1. Wooi manages those chains itself with plain git and gh — no extra stacking CLI needed. 모든 작업이 독립적이지는 않습니다 — 2번 작업이 1번 위에서 이어져야 할 때가 있죠. Wooi 는 그 체인을 git 과 gh 만으로 직접 관리합니다. 별도 스택 도구가 필요 없습니다.
  • Stack a workspace워크스페이스 쌓기 — pick Stack a new workspace from a workspace's menu; the new one branches off that workspace's branch and its PR targets that branch instead of the default branch. 워크스페이스 메뉴에서 Stack a new workspace 를 고르면 그 브랜치에서 분기한 워크스페이스가 생기고, PR 도 기본 브랜치가 아닌 그 부모 브랜치를 대상으로 열립니다.
  • Or let the agent stack it에이전트가 쌓게 두기 — create_stacked_workspace opens the next workspace on top of the current branch when the work just finished is a complete, reviewable unit. See Agent orchestration below. create_stacked_workspace 는 방금 끝낸 작업이 리뷰 가능한 한 덩어리일 때 현재 브랜치 위에 다음 워크스페이스를 엽니다. 아래 에이전트 오케스트레이션을 참고하세요.
  • Stack overview스택 한눈에 — a Stack button in the header lists every branch in the chain with its PR state, PR number, and ahead/behind counts. Click to jump, or open a PR for a branch that doesn't have one. 헤더의 Stack 버튼이 체인의 모든 브랜치를 PR 상태·PR 번호·ahead/behind 와 함께 보여 줍니다. 클릭해 이동하거나, PR 이 없는 브랜치는 그 자리에서 PR 을 엽니다.
  • RestackRestack — rebase a workspace onto the latest parent branch and push with --force-with-lease. Conflicts stop in the worktree so you can resolve them there. 최신 부모 브랜치 위로 rebase 하고 --force-with-lease 로 push 합니다. 충돌이 나면 worktree 에 멈춰 있어 거기서 해결하면 됩니다.
  • Merge cascade병합 캐스케이드 — when a parent PR merges, Wooi retargets each child PR's base to the grandparent branch and rebases the children onto it, so the rest of the stack stays valid. 부모 PR 이 병합되면 각 자식 PR 의 base 를 조부모 브랜치로 옮기고 자식 브랜치를 그 위로 rebase 해, 스택 나머지가 그대로 유효하게 남습니다.
  • Detected, not just declared선언이 아니라 감지 — if an agent builds a chain itself with git checkout -b and gh pr create, Wooi reconstructs the stack from the PRs' base links and shows it the same way. 에이전트가 git checkout -b 와 gh pr create 로 직접 체인을 만들어도, PR 의 base 링크에서 스택을 복원해 똑같이 보여 줍니다.
  • The parent is the default base — for everyone기본 base 는 누가 열든 부모 — stacking a workspace records the parent as that branch's merge base, so a bare gh pr create — yours or an agent's — targets the parent. If a PR still lands on the wrong base, Wooi says so and offers to retarget it instead of quietly dropping the stack. 워크스페이스를 스택으로 만들면 그 브랜치의 merge base 에 부모를 기록합니다. 그래서 그냥 실행한 gh pr create 도 — 사용자가 치든 에이전트가 치든 — 부모 브랜치를 향합니다. 그래도 엉뚱한 base 로 열렸다면, 조용히 스택을 잃는 대신 알려 주고 리타겟할지 물어봅니다.
🤖

Agent orchestration에이전트 오케스트레이션

  • A built-in MCP server, nothing to configure설정 없이 붙는 내장 MCP 서버 — Wooi attaches a server named wooi to every Claude Code and Codex session it starts. The agent doesn't just edit files in its worktree; it can drive Wooi itself — split a task, open the workspaces for the pieces, stack them in dependency order, and pass results along the chain. Wooi 가 띄우는 모든 Claude Code·Codex 세션에 wooi 서버가 붙습니다. 에이전트는 자기 worktree 의 파일만 고치는 게 아니라 Wooi 자체를 조종합니다 — 작업을 쪼개고, 조각마다 워크스페이스를 열고, 의존 순서대로 쌓고, 결과를 체인을 따라 넘깁니다.
  • See the neighbours first옆자리부터 확인 — check_related_work lists the other workspaces open on this repo and the paths each is changing, flags overlaps with what this agent plans to touch, and tells it to check with you first. Paths only — diffs are never shared between workspaces. check_related_work 는 이 리포에 열려 있는 다른 워크스페이스와 각각이 바꾸는 경로를 알려 주고, 이 에이전트가 건드리려는 경로와 겹치면 사용자에게 먼저 물어보라고 안내합니다. 넘어가는 건 경로뿐 — diff 는 워크스페이스 사이를 넘지 않습니다.
  • Fan out or stack up펼치거나 쌓거나 — create_workspace starts an independent workspace off the default branch; create_stacked_workspace starts a child off the committed tip of the current branch. Either can be handed a first message that starts the new agent's turn immediately. create_workspace 는 기본 브랜치에서 독립 워크스페이스를, create_stacked_workspace 는 현재 브랜치의 커밋된 끝에서 자식 워크스페이스를 만듭니다. 둘 다 첫 메시지를 함께 넘겨 새 에이전트의 턴을 바로 시작할 수 있습니다.
  • Talk along the chain체인을 따라 주고받기 — report_to_parent records a result for the parent without interrupting it, check_stacked_work lists the children with their branch, PR state, and latest report, and notify_child sends an update that starts a turn in a child. report_to_parent 은 부모의 턴을 끊지 않고 결과를 기록하고, check_stacked_work 는 자식들의 브랜치·PR 상태·최신 보고를 나열하며, notify_child 는 자식에게 소식을 보내 턴을 시작합니다.
  • Fenced in울타리 — most tools act only on the calling workspace; tools that take a workspace id can only name one the caller created. Read-only tools run without a prompt; state-changing ones follow the workspace's permission mode and show an approval card. 대부분의 도구는 호출한 워크스페이스에만 작용하고, 워크스페이스 id 를 받는 도구는 호출자가 직접 만든 것만 겨냥할 수 있습니다. 읽기 전용 도구는 승인 없이 돌고, 상태를 바꾸는 도구는 권한 모드를 따라 승인 카드를 띄웁니다.
🔍

PR reviewPR 리뷰

  • A diff you review on, not a transcript you read읽는 로그가 아니라 작업하는 diff — three panes: the changed files with a count of findings on each, the full diff in the middle, and a findings / activity sidebar. Every agent reviews PRs now — what was missing is somewhere to work the result. 3분할입니다. 왼쪽은 변경 파일과 파일별 지적 개수, 가운데는 diff 전체, 오른쪽은 총평/활동 사이드바. PR 리뷰는 이제 어떤 에이전트든 합니다. 없던 건 그 결과를 다룰 화면입니다.
  • Findings land on the lines they're about지적은 해당하는 줄 위에 — each one is anchored to its hunk and rendered as a card right there in the diff, with a severity badge and a markdown body. If an agent cites a line that isn't in the diff, the card says so and shows where it moved to — you catch a misplaced comment before it goes out, not after. 각 지적이 자기 hunk 에 앵커되어 심각도 배지와 마크다운 본문을 단 카드로 diff 안에 바로 붙습니다. 에이전트가 diff 에 없는 줄을 짚으면 카드가 그 사실과 옮겨진 위치를 알려 줍니다. 엉뚱한 줄에 달린 코멘트를 나간 뒤가 아니라 나가기 전에 잡습니다.
  • Curate before you post게시 전에 추리기 — Edit reworks the wording inline, Discard drops what you don't want, Comment posts that finding on its own. Or tick the ones you want and send the batch — each goes out as its own review comment, and posted cards go quiet with a link to the comment on GitHub. Edit 로 문장을 그 자리에서 고치고, Discard 로 안 달 것을 버리고, Comment 로 그 지적만 올립니다. 원하는 것만 체크해 한 번에 올릴 수도 있습니다. 각각 개별 리뷰 코멘트로 나가고, 게시된 카드는 GitHub 코멘트 링크만 남기고 조용해집니다.
  • Keep your place in a big diff큰 diff 에서 자리 잃지 않기 — tick a file as viewed and it collapses out of the way. The mark is stored against a fingerprint of that file's contents, so a new commit that changes the file puts it back to unviewed on its own — and files that didn't change stay checked. 파일에 봤음 표시를 하면 접혀 비켜 줍니다. 이 표시는 파일 내용의 지문과 함께 저장되므로, 새 커밋이 그 파일을 바꾸면 저절로 안 본 상태로 돌아가고 바뀌지 않은 파일은 표시가 그대로 남습니다.
  • Start a review리뷰 시작 — hit Review PR on the Overview board, pick a repo and one of its open PRs (or type a number), and say what you want looked at. A review gets its own row in the sidebar and runs alongside your workspaces. Overview 보드의 Review PR 을 누르고 리포와 열린 PR 을 고른 뒤(번호 직접 입력도 됩니다) 무엇을 봐 주면 좋을지 적습니다. 리뷰는 사이드바에 자기 행을 갖고 워크스페이스 옆에서 나란히 돕니다.
  • Claude or CodexClaude 또는 Codex — pick the agent when you start; the review stays on it, and follow-up turns resume the same session. 시작할 때 에이전트를 고르면 리뷰는 끝까지 그 에이전트로 돌고, 후속 질문도 같은 세션을 이어받습니다.
  • Its own worktree전용 worktree — the PR head is checked out into a dedicated review worktree, so the agent can read code outside the changed hunks without touching the checkout you're working in. PR head 를 별도 리뷰 worktree 에 체크아웃해, 지금 작업 중인 체크아웃은 건드리지 않으면서 변경된 hunk 바깥의 코드까지 읽게 합니다.
  • Activity timeline활동 타임라인 — replies to comments you posted and new commits on the PR are polled automatically and land in the timeline; ask a follow-up and the review picks up from there. 게시한 코멘트의 답글과 PR 의 새 커밋을 주기적으로 가져와 타임라인에 쌓습니다. 이어서 질문하면 그 지점부터 다시 이어집니다.
  • Verdicts판정 — comment, approve, or request changes. Unposted findings can go up with the verdict — comments first, and the verdict is held back if any of them fail. Approve / request changes are hidden on your own PR, which GitHub rejects anyway. comment · approve · request changes 를 제출합니다. 안 올린 지적은 판정과 함께 올릴 수 있고 — 코멘트가 먼저 올라가며, 하나라도 실패하면 판정은 보류됩니다. 내 PR 에서는 approve/request changes 를 숨깁니다(GitHub 이 거부하므로).
  • Persistent영속 — reviews survive restarts and can be archived, restored, or deleted; deleting cleans up the review worktree too. 앱을 껐다 켜도 남고 아카이브·복원·삭제할 수 있습니다. 삭제하면 리뷰 worktree 도 함께 정리됩니다.
🎛️

Agent backends에이전트 백엔드

  • Backend-specific controls백엔드별 컨트롤 — models, reasoning effort, permission modes, slash commands, and account details all come from the selected backend, so a workspace only shows controls that actually work there. 모델·reasoning effort·권한 모드·슬래시 명령·계정 정보가 전부 선택한 백엔드에서 옵니다. 워크스페이스에는 거기서 실제로 동작하는 컨트롤만 뜹니다.
  • Permission modes, cycled with Shift+TabShift+Tab 으로 순환하는 권한 모드 — Claude Code offers default, accept edits, plan, and auto; Codex offers read only, auto, full access, and plan. Prompts offer "Always allow" alongside Allow/Deny — Enter = Allow, Esc = Deny. Claude Code 는 default·accept edits·plan·auto 를, Codex 는 read only·auto·full access·plan 을 제공합니다. 권한 프롬프트는 Allow/Deny 외에 "Always allow" 도 제공합니다 — Enter=Allow / Esc=Deny.
  • Capabilities only one side has한쪽에만 있는 기능 — /rewind (roll code back to a file checkpoint) and /btw (a side question that doesn't derail the turn) appear where the backend supports them, and mid-turn steering is used where it exists instead of being queued. /rewind(파일 체크포인트로 되돌리기)와 /btw(턴을 흐트러뜨리지 않는 곁가지 질문)는 백엔드가 지원할 때 나타나고, 턴 중간 steering 도 되는 쪽에서는 큐잉 대신 그대로 씁니다.
  • Rate limits, normalized정규화된 레이트리밋 — account usage from either backend shows in one status line, pinned to the window that actually paces you — Claude's 5-hour session window, Codex's weekly one — so the number doesn't swap out from under you. 양쪽 백엔드의 계정 사용량을 상태줄 하나로 보여 주되, 실제로 페이스를 좌우하는 창에 고정합니다(Claude 는 5시간 세션 창, Codex 는 주간 창). 볼 때마다 다른 숫자로 바뀌지 않습니다.
  • Your MCP servers come along내 MCP 서버도 그대로 — servers configured in your own Claude/Codex CLI setup are resolved and injected into the session alongside Wooi's own wooi server. Claude·Codex CLI 에 설정해 둔 MCP 서버를 읽어 Wooi 자체 wooi 서버와 함께 세션에 붙입니다.

Workspaces워크스페이스

  • No default prompt기본 프롬프트 없음 — the input box starts empty; the session begins only when you send your first message. 입력창은 빈 상태로 시작하고, 첫 메시지를 보낼 때 비로소 세션이 시작됩니다.
  • Automatic creation자동 생성 — workspaces get an auto-generated name (like witty-otter) and branch off the default branch. Turn on manual setup to choose the name and base branch yourself. 자동 생성된 이름(witty-otter 등)을 받고 기본 브랜치에서 분기됩니다. 직접 입력을 켜면 이름·베이스 브랜치를 직접 고를 수 있습니다.
  • Choose Claude Code or CodexClaude Code 또는 Codex 선택 — pick the coding agent when creating a workspace, and change your mind with /agent any time before the first message. After that the workspace keeps that agent, and stacked workspaces inherit their parent's. 워크스페이스를 만들 때 코딩 에이전트를 고르고, 첫 메시지 전까지는 /agent 로 바꿀 수 있습니다. 그 뒤로는 그 에이전트를 유지하며, 스택으로 만든 워크스페이스는 부모의 에이전트를 물려받습니다.
  • Per-workspace model & effort워크스페이스별 모델·effort — set from the status line or by typing /model, /effort, and /fast. Options depend on the selected agent and model. 상태줄에서 고르거나 /model·/effort·/fast 로 바꿉니다. 선택지는 에이전트와 모델에 따라 달라집니다.
  • Sessions resume across restarts재시작 간 세션 resume — your conversation context is restored, so the next message continues where you left off. 대화 맥락이 복원되어, 재시작 후 첫 메시지에서 하던 작업을 이어갑니다.
  • Carried files파일 전달(carry) — a new worktree only contains git-tracked files, so list the ignored ones you need (.env, CLAUDE.local.md, …) per repo. Copy gives each workspace its own version, Link shares one original. 새 worktree 에는 git 이 추적하는 파일만 들어오므로, 필요한 무시 파일 (.env, CLAUDE.local.md 등)을 리포마다 적어 둡니다. Copy 는 워크스페이스마다 자기 사본을, Link 는 원본 하나를 공유합니다.
👁️

Parallel-session visibility병렬 세션 가시화

  • Status at a glance한눈에 보는 상태 — the sidebar distinguishes running (spinner), awaiting permission (yellow shield), and unread responses (blue dot). 사이드바에서 실행 중(spinner)·권한 대기(노란 방패)·미확인 응답(파란 점)을 구분해 보여줍니다.
  • OS notifications & Dock badgeOS 알림 · Dock 배지 — when the window is inactive, completions / errors / permission requests appear as notifications and a Dock badge count. 창이 비활성이면 완료·에러·권한 요청을 OS 알림으로 띄우고 Dock 배지에 집계합니다.
  • Jump to what needs you확인 필요한 곳으로 이동 — "Needs input" / "Next unread" buttons jump straight to the session that needs you. "Needs input / Next unread" 버튼으로 사용자 확인이 필요한 세션으로 바로 이동합니다.
  • Overview boardOverview 보드 — lists every active session with status filters (All / Running / Needs input / Unread / Idle) and a Stop all action. 모든 활성 세션을 상태별 필터(All / Running / Needs input / Unread / Idle)로 훑고 Stop all 로 일괄 중단합니다.
  • Updates that wait for you기다려 주는 업데이트 — restarting mid-turn would cut an agent off, so a ready update can be installed now or held with Restart when work finishes — Wooi waits until every workspace is idle, then restarts on its own. 턴이 도는 중에 재시작하면 에이전트가 끊깁니다. 그래서 준비된 업데이트를 지금 설치 하거나 Restart when work finishes 로 미룰 수 있습니다 — 모든 워크스페이스가 잠잠해지면 알아서 재시작합니다.

Work area작업 영역

  • All filesAll files — a file tree of the worktree with a read-only, syntax-highlighted viewer. worktree 파일 트리와 읽기 전용·구문 강조 뷰어.
  • ChangesChanges — a per-file diff against the base branch (same as a PR diff), covering commits + staged + unstaged + untracked. A Create PR button opens GitHub's PR page. base 브랜치 대비 파일별 diff(PR diff 와 동일). 커밋 + staged + unstaged + untracked 를 모두 포함하고, Create PR 버튼이 PR 작성 화면을 엽니다.
  • CheckCheck — CI check results for the PR on the current branch. 현재 브랜치 PR 의 CI 체크 결과.
  • TerminalTerminal — a per-workspace login-shell terminal that survives workspace switches, preserving running commands and shell state. workspace 별 로그인 셸 터미널. 전환했다 돌아와도 실행 중이던 명령과 셸 상태가 유지됩니다.

Composing messages메시지 작성

  • Slash-command autocomplete슬래시 명령 자동완성 — type / to see the commands available for the workspace's selected agent. / 를 치면 워크스페이스에서 선택한 에이전트가 지원하는 명령 목록이 뜹니다.
  • Inline shell commands인라인 셸 명령 — start a message with ! to run it as a shell command, with output shown right in the chat. 메시지를 ! 로 시작하면 셸 명령으로 실행되고 결과가 채팅에 바로 표시됩니다.
  • Image attachments이미지 첨부 — paste or drop images into the input box to send them along. 입력창에 이미지를 붙여넣거나 끌어다 놓으면 함께 전송됩니다.
  • Status line & auto-compact상태줄 · 자동 압축 — branch · directory · model · effort · context usage always shown; long conversations auto-compact, or run /compact manually. 브랜치 · 디렉토리 · 모델 · effort · 컨텍스트 사용량이 항상 표시되고, 길어지면 자동 압축되거나 /compact 로 수동 압축합니다.
  • Drafts, queueing & shortcuts초안·큐잉·단축키 — in-progress messages survive workspace switches; queue follow-ups while a turn runs; ↑/↓ recall messages, ⌘1–9 and ⌘↑ ⌘↓ switch workspaces, ⌘[ goes back. 작성 중 메시지는 전환에도 유지되고, 실행 중 후속 메시지를 큐에 넣습니다. ↑/↓ 로 이전 메시지, ⌘1–9 / ⌘↑ ⌘↓ 로 전환하고, ⌘[ 로 직전 워크스페이스로 돌아갑니다.
Get started시작하기

Install in a couple of minutes몇 분이면 설치 완료

One brew command, then a quick onboarding. brew 명령 한 줄, 그리고 간단한 온보딩이면 됩니다.

1

Install with HomebrewHomebrew 로 설치

Homebrew puts Wooi.app straight into Applications. Homebrew 가 Wooi.app 을 Applications 에 바로 설치합니다. 

brew install --cask youngminnnn/tap/wooi

Rather do it by hand? Download the latest .dmg and drag Wooi into Applications. Older builds live on the Releases page. 직접 설치하시겠어요? 최신 .dmg 를 받아 Wooi 를 Applications 로 드래그합니다. 이전 빌드는 Releases 페이지에 있습니다.

2

Onboarding: consent & sign in온보딩: 동의 & 로그인

Consent to the Terms/Privacy, then connect Claude Code or Codex — you only need one. Sign-in finishes in-app; Codex accepts ChatGPT or an OpenAI API key. GitHub is optional at this point: skip it and start working, and Wooi will ask the first time you open a PR, merge, stack a branch or check CI, then resume what you were doing. 약관·개인정보처리방침에 동의한 뒤 Claude Code 또는 Codex를 연결합니다. 둘 중 하나만 있으면 되며, Codex는 ChatGPT 또는 OpenAI API 키로 연결할 수 있습니다. GitHub 은 이 단계에서 건너뛸 수 있습니다 — 바로 작업을 시작하면, PR 생성·머지·스택·Check 를 처음 쓰는 순간 Wooi 가 연결을 요청하고 연결 후 원래 하려던 동작을 이어서 실행합니다.

Privacy & Data개인정보 / 데이터

Your code stays yours코드는 당신의 것

🚫

No analytics분석 없음

Wooi has no servers of its own and collects no analytics or telemetry. Wooi 는 자체 서버가 없고 분석·텔레메트리를 수집하지 않습니다.

🔗

Direct to providers공급자로 직접 전송

Prompts & code go to the selected agent's provider — Anthropic for Claude Code or OpenAI for Codex. PR metadata goes to GitHub via the gh CLI. 프롬프트·코드는 선택한 에이전트의 제공자(Claude Code는 Anthropic, Codex는 OpenAI)에게 전송됩니다. PR 메타데이터는 gh CLI로 GitHub에 전송됩니다.

💾

Local only로컬에만 저장

Settings & transcripts are stored locally in ~/Library/Application Support/Wooi/. 설정·대화 기록은 ~/Library/Application Support/Wooi/ 에만 저장됩니다.
