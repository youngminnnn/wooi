# 스택 리뷰

[English](./stack-review.md) · **한국어**

Wooi는 쌓아 올린 풀 리퀘스트 묶음을 하나의 단위로 리뷰합니다. 리뷰는 한 번 돌고, 모든 레이어의
diff를 동시에 보며, 스택 수준에서만 나오는 질문에 답합니다 — 레이어 경계가 맞는지, 각 레이어가
혼자 설 수 있는지, 아래층의 지적이 위층의 작업을 무효로 만드는지.

이 문서는 그 기능의 설계입니다. 무엇을 정했고, 왜 그렇게 정했고, 어떻게 만드는지를 담습니다.

## 왜 리뷰 N번이 아닌가

스택의 PR을 하나씩 따로 리뷰하는 것은 지금 모든 도구가 하는 일이고 Wooi도 마찬가지였습니다.
GitHub은 2026-07-30에 stacked pull request를 퍼블릭 프리뷰로 내면서 각 PR 상단에 스택 지도를
붙였지만, 그 지도는 보여 줄 뿐 아무것도 리뷰하지 않습니다. 그 결과 리뷰어가 스택을 볼 때 실제로
품는 질문에는 답할 주체가 없습니다.

- **순서.** 레이어 3이 레이어 4에서야 도입되는 심볼·마이그레이션·설정값을 쓰고 있지 않은가?
  그렇다면 레이어 3은 혼자 머지될 수 없고 순서가 잘못된 것입니다.
- **독립성.** 레이어 2를 레이어 3을 읽지 않고 이해할 수 있는가? 위층을 읽어야만 말이 되는 층은
  층이 아닙니다.
- **무효화.** 아래층에 변경을 요청하면 그 위에서 무엇이 함께 움직여야 하는가?
- **알갱이 크기.** 두 층이 하나여야 하는가, 한 층이 둘이어야 하는가?
- **되돌림.** 나중 층이 앞선 층이 넣은 것을 되돌리거나 다시 쓰지 않았는가? 그 작업은 아래로
  접혔어야 합니다.

전부 diff **사이의** 관계에 대한 진술입니다. diff 하나만 보는 리뷰는 이런 답을 낼 수 없고, N개의
diff를 차례로 보고 결과를 이어 붙이는 리뷰도 마찬가지입니다 — 레이어 4를 읽을 때쯤이면 레이어 3을
잊었고, 출력 어디에도 "이 두 층은 반으로 쪼갠 같은 변경"이라고 말할 자리가 없습니다.

그래서 이 기능의 규칙은 이렇습니다. **기존 PR 리뷰를 N번 돌려 출력을 이어 붙이는 것은 스택 리뷰가
아니며, 그렇게 만들지 않습니다.** 위의 스택 질문들이 산출물이고, 아래의 모든 결정은 그것을 가능하게
하는 데서 따라옵니다.

## 스택은 어디서 오는가

Wooi에는 스택 모델이 둘 있고, UI는 이미 둘을 같은 방식으로 그립니다.

1. **워크스페이스** 체인 — 각자 워크트리를 갖고 `parentWorkspaceId`로 이어집니다.
2. 한 워크트리 안의 **브랜치** 체인(`Workspace.stack`) — "Split here"가 만듭니다.

스택 리뷰는 멤버십을 기존 추상을 통해서만 읽습니다.

| 출처 | 추상 |
| --- | --- |
| 워크트리 안 브랜치 스택 | `workspaceStack(ws)` (`src/shared/types.ts`) |
| 워크스페이스 체인 | `workspaceStackMembers(all, id)` + `orderByStack()` |
| GitHub이 들고 있는 스택 객체 | `buildStackFromGhStack()` (`src/main/stack.ts`) |
| GitHub의 열린 PR(Wooi 밖에서 만든 스택) | `buildStackFromPrs()` (`src/main/stack.ts`) |

`src/main/review/stackResolve.ts`가 이들을 부르는 리뷰 서브시스템 안의 유일한 파일이고, 나머지에게
넘기는 것은 딱 하나의 모양입니다 — 아래부터 정렬된 PR 번호 목록. 그 아래에서는 어떤 모델이
그 목록을 만들었는지 아무도 모릅니다.

이 단일 지점은 기능이 머지되기도 전에 값을 했습니다. 작업 중에 #278이 GitHub 스택 연동의 읽기
경로를 넣어, 앱의 흡수 경로가 GitHub에 먼저 묻고 base 링크 복원으로 떨어지게 바뀌었습니다. 스택
리뷰도 같은 순서를 따르는데, 그 채택은 `stackResolve.ts`의 함수 하나였고 서브시스템의 나머지는
움직이지 않았습니다.

순서는 흡수보다 리뷰에서 더 중요합니다. GitHub은 엔트리마다 `position`을 명시하므로, 리타겟이
아직 안 밀려 base 체인이 잠시 끊긴 순간에도 스택이 살아남습니다. base 링크 복원은 그러지
못합니다 — 2층이 아직 `main`을 가리키고 있으면 2·3층만 돌려주고 1층을 조용히 떨어뜨립니다.
스택을 리뷰하려던 사용자가 그 일부만 리뷰하게 되는데, 화면에는 그 사실이 어디에도 안 나옵니다.
바로 그 모양의 테스트가 있습니다.

## 결정

### 스택 전체에 세션 하나

스택 리뷰는 레이어 목록을 가진 **`ReviewSession` 하나**입니다. 레이어마다 세션을 만들고 그 위에
조율자를 두는 방식이 아닙니다.

대안은 검토했고 구체적인 실패로 접었습니다. 조율하는 부모는 결국 모든 diff를 자기가 다시 읽거나 —
그러면 레이어별 세션은 한 일이 없습니다 — 그 요약을 가지고 일합니다. 요약을 가지고는 이 기능이
존재하는 이유인 그 질문에 답할 수 없습니다. "레이어 3의 42번째 줄이 `resolveStackAnchor`를 부르는데
그것을 추가하는 것은 레이어 4다"는 한쪽 diff의 특정 줄과 다른 쪽 diff의 특정 hunk에 대한 주장입니다.
가질 만한 가치가 있을 만큼 짧은 레이어 4의 요약에는 그 내용이 들어 있지 않습니다.

세션이 하나면 `ReviewSession`이 `agentBackend`·`model`·`effort`를 시작 시점에 박아 두는 이유도
그대로 살아남습니다. 후속 턴은 같은 대화를 resume하고, resume 세션 id는 그것을 발급한 백엔드에서만
유효합니다. 세션이 하나면 대화도 하나라 규칙이 그대로입니다. N+1개면 "이 리뷰를 이어서"에 답이
없어져, 레이어들이 하나라는 전제 위에 선 기능이 사용자에게 어느 레이어냐고 되묻게 됩니다.

진짜로 PR 단위인 것은 GitHub을 향한 상태이고, 그것이 레이어 레코드로 갑니다.

```ts
export interface ReviewLayer {
  prNumber: number
  prUrl: string
  prTitle: string
  prAuthor: string
  /** GitHub은 자기 PR 승인을 막는다 — 스택이 아니라 레이어마다 판정한다. */
  viewerIsAuthor: boolean
  /** 이 PR의 인라인 코멘트가 쓰는 commit_id. */
  headSha: string
  headRefName: string
  baseRefName: string
  /** 병합된 레이어는 기록으로 남되 폴링·재조회에서 빠진다. */
  merged: boolean
  /** 이 PR의 답글 폴링 워터마크(ISO). */
  lastSeenAt: string | null
  lastSeenHeadSha: string
  /** 이 레이어 하나에 대한 총평. 판정 본문이 PR마다 필요하다. */
  summary: string
  /** 이 PR에 제출한 판정. 제출이 PR 단위이므로 기록도 PR 단위다. */
  lastSubmission: ReviewSubmission | null
}

export interface ReviewSession {
  // …
  /** 아래→위. PR 하나짜리 리뷰는 원소가 하나인 스택이다. */
  layers: ReviewLayer[]
}
```

마지막 줄이 핵심입니다. **PR 하나짜리 리뷰는 원소가 하나인 스택**이고, 이는 `workspaceStack()`이
스택이 아닌 워크스페이스에 단일 엔트리를 합성해 주는 것과 같은 규칙입니다. 매니저·프롬프트·앵커링·
화면이 한 경로로 돌고, "스택" 분기가 평소 경로 옆에 덧붙은 특수 케이스가 아니라 **그것이 곧 평소
경로**입니다. 반대 방향 — 단일 PR 경로를 두고 스택 경로를 나란히 새로 만드는 것 — 은 둘이 갈라질
것이고, 테스트가 붙어 있는 쪽이 단일 PR 경로라서 접었습니다.

`ReviewSession`의 `prNumber`·`prUrl`·`prTitle`·`prAuthor`·`viewerIsAuthor`·`headSha`·`baseRefName`·
`lastSubmission`은 없어지고, 스키마 마이그레이션(v20 → v21)이 그것들을 원소 하나짜리 `layers`로
접습니다. `normalizeShape()`도 `layers`를 메웁니다 — 구버전 빌드가 이미 마이그레이션된 파일에
이어서 쓰는 경우를 막기 위한 것으로, #267에서 추가한 방어와 같은 이유입니다.

세션의 정체성 — 사이드바 이름, 워크트리 키 — 은 `stackHead(session)`, 즉 **맨 위** 레이어에서
옵니다. 맨 위가 가장 늦게 병합되므로 리뷰의 이름으로 안정적입니다. 맨 아래는 승인 몇 분 뒤에
병합돼 닫히는 일이 흔합니다.

### 컨텍스트 예산

5층짜리 스택은 아주 클 수 있고 모델의 컨텍스트는 하나입니다. 예산은 단일 총량
(`MAX_DIFF_CHARS`, 300,000자 — 희소한 것은 컨텍스트지 PR 개수가 아니므로 그대로 둡니다)이고,
정해진 순서로 씁니다.

**1. 스택 골격은 언제나 전부 싣습니다.** 레이어마다 PR 번호·제목·base → head·커밋 제목, 그리고
변경 파일 한 줄씩(`경로 상태 +a −d`). 5층 200파일짜리 스택에서도 몇 KB이고, 프롬프트에서 가장
값이 큽니다 — 순서·알갱이 크기·되돌림 질문은 hunk 내용보다 **어느 레이어가 어느 파일을 건드리는가**
에서 대부분 나옵니다. 골격 끝에는 **레이어 교차 파일 표**가 붙습니다. 둘 이상의 레이어가 건드린
경로와 그 레이어들을 적은 것으로, 되돌림 질문을 찾는 대신 계산해 둔 것입니다.

**2. 번호가 박힌 diff는 필요에 따라 배분합니다.** 레이어마다 바닥을 깔아(어느 층도 안 보이는 일이
없게) 남은 몫을 크기에 비례해 나눕니다. 레이어 안에서는 교차 파일 표에 있는 파일을 먼저 싣습니다 —
hunk 수준의 세부가 필요한 질문을 그것들이 지고 있기 때문입니다. 못 들어간 파일은 이름을 남깁니다.

**3. 잘림은 보고하지, 조용히 넘어가지 않습니다.** 프롬프트가 빠진 파일을 전부 이름으로 적고, 리뷰
워크트리에서 `git diff <base-ref>...<head-ref> -- <path>`로 읽으라고 알려 줍니다(그 워크트리에는
모든 레이어의 head가 로컬 ref로 들어와 있습니다). 세션은 `truncatedFiles`를 기록하고, 리뷰 화면이
몇 개가 안 실렸는지 보여 줍니다. 스택의 60%만 조용히 보고 "괜찮아 보인다"고 말하는 리뷰는 무엇을
안 읽었는지 말하는 리뷰보다 나쁩니다.

**4. 골격조차 안 들어가면 리뷰를 시작하지 않습니다.** 반토막 난 프롬프트를 보내는 대신 크기를
알려 주며 실패합니다. **레이어 10개**라는 상한도 있습니다. 그보다 크면 스택 자체가 문제입니다.

### 지적은 어디에 달리는가

인라인 코멘트는 그 줄을 담고 있는 PR에 반드시 달려야 합니다. 아니면 GitHub이 422로 거절합니다 —
그리고 422보다 나쁜 경우가 있습니다. 같은 경로·같은 줄 번호가 두 레이어에 있으면 요청이 통과하고
**엉뚱한 PR에 조용히 달립니다.** 앵커링이 이 기능에서 가장 위험한 부분이므로 규칙을 좁게 잡습니다.

- `ReviewAnchor`에 `prNumber`가 들어갑니다. 그것 없는 앵커는 존재할 수 없습니다.
- 스키마가 모든 인라인 지적에 `prNumber`를 요구하고, 렌더한 diff의 파일 헤더마다 PR을 박습니다
  (`=== [#13] src/main/store.ts (modified)`). 모델은 경로를 읽는 바로 그 줄에서 번호를 읽습니다.
- **레이어 사이로 흘러가지 않습니다.** 에이전트가 #13을 지목했는데 그 파일이나 줄이 #13의 diff에
  없으면, 그 지적은 이유와 함께 전반 지적으로 강등됩니다. #14로 다시 시도하지 않습니다. 스냅
  (`SNAP_DISTANCE`, 3줄)도 지목한 레이어 안에서만 일어납니다.
- `prNumber`가 없으면 그 경로를 가진 레이어를 찾습니다. 정확히 하나면 그것입니다. 여럿이면 그중
  **그 줄이 그 면에 실제로 있는** 레이어가 정확히 하나일 때만 채택하고, 아니면 강등합니다.
  `store.ts`를 둘 다 고친 두 레이어 중 하나를 찍는 것이 코멘트가 엉뚱한 PR에 가는 경로입니다.

**스택 자체에 대한 지적** — "레이어 2와 3은 하나의 변경이다", "레이어 3이 레이어 4에 의존한다" —
은 어느 줄에도 속하지 않습니다. 별도의 종류입니다.

```ts
export interface ReviewFinding {
  // …
  anchor: ReviewAnchor | null
  /** 이 지적이 게시될 PR. 인라인이면 anchor.prNumber 와 같다. */
  prNumber?: number
  /** 이 지적이 관련짓는 레이어들. 스택 지적일 때만 비어 있지 않다. */
  stackPrNumbers?: number[]
}
```

스택 지적은 **그것이 지목한 가장 아래 레이어**에 타임라인 코멘트로 올라갑니다. 먼저 바뀌어야 하는
층이고, 행동을 요구받는 작성자가 있는 곳입니다. 그리고 코멘트 자체에서 그 사실이 분명해야 합니다.
`buildFindings`가 본문 앞에 머리글 한 줄을 붙입니다.

```
**Stack review** · #12 → #13 → #14

<에이전트가 쓴 내용>
```

이렇게 하면 게시는 지금까지처럼 **그대로(verbatim)** 나가고, 사용자는 무엇이 올라갈지 정확히 보며,
다른 텍스트와 똑같이 고치거나 지울 수 있습니다. 인라인 지적을 강등할 때 원래 위치를 앞에 붙이는
지금 코드와 같은 방식입니다.

리뷰 화면에서는 스택 지적이 레이어별 전반 지적 위에 자기 구역을 갖고, 지목한 가장 아래 레이어 순으로
놓입니다. 이 기능의 요점이므로 목록 맨 아래로 가지 않습니다.

### 판정

GitHub에서 `ReviewVerdict`는 PR 단위이고 체인을 승인하는 API는 없습니다. 그러므로 스택을 승인한다는
것은 리뷰를 N번 제출한다는 뜻입니다. 설계는 그것을 감추지 않고, 팬아웃을 드러내며 복구 가능하게
만듭니다.

제출 모달은 **스택에 대한 결정 하나**를 받고 그것으로 무엇을 할지 보여 줍니다 — 레이어마다 한 줄,
거기 제출될 판정이 적혀 있고 줄마다 고칠 수 있습니다.

- 내가 쓴 레이어는 `comment`로 떨어지고 이유를 적습니다(`SELF_REVIEW_BLOCKED`, 공유 상수).
  레이어 단위입니다 — 둘이 함께 쌓은 스택이면 내 것과 남의 것이 섞여 있습니다.
- 병합된 레이어는 빠지고, 그렇다고 표시됩니다.
- **스택 총평은 맨 위 레이어에 한 번만** 그 레이어의 판정과 함께 올라갑니다. 나머지 레이어는
  아티팩트의 자기 총평을 받고, 전체 평가가 어디 있는지 가리키는 문장이 앞에 붙습니다. 같은 문단을
  다섯 PR에 올리는 것은 소음이고, 본문 없는 `request-changes`는 GitHub이 거절합니다.
- 제출은 순차이고, **성공은 레이어마다 그 자리에서 기록**됩니다(`ReviewLayer.lastSubmission`).
  레이어 3이 실패해도 1·2는 제출된 채로 남고, 모달이 남은 것을 보여 주며 다시 내면 나머지만
  나갑니다. `EMPTY_RESUBMIT_BLOCKED`도 지금 존재하는 이유 그대로 레이어마다 걸립니다.

### 후속 턴

`detectNewActivity`와 `detectOutdatedComments`는 PR 단위이고 그대로 둡니다. 폴링이 병합되지 않은
레이어마다 자기 워터마크로 한 번씩 돌고, 활동 항목에 `prNumber`가 붙어 타임라인이 어느 레이어의
일인지 적을 수 있습니다.

문제는 단일 PR에는 없는 경우입니다. **작성자가 레이어 1에 push하면 그 위가 전부 rebase됩니다.**
스택의 모든 head sha가 바뀌고 인라인 코멘트 대부분이 outdated가 되지만, 흔한 경우에 레이어 1 위에서
실제로 바뀐 것은 없습니다. 거기서 스택 전체를 다시 읽으면 비싸고, 진짜 변경이 소음에 묻힙니다.
그래서 후속 턴은 이렇게 다시 읽습니다.

1. 레이어 *i*의 head가 바뀌면 레이어 *i*와 **그 위의 모든 레이어**가 무효가 됩니다 — 그 diff들은
   움직인 base 위에서 계산됩니다. *i* 아래는 다시 받지 않습니다.
2. 무효가 된 위쪽 레이어마다 새로 받은 diff를 저장된 것과 내용 지문으로 비교합니다. **같으면 순수
   restack**입니다. 그 레이어의 지적은 그대로 두고 `headSha`만 갱신하며(다음 인라인 코멘트가 새
   `commit_id`를 씁니다), 타임라인에는 "레이어 2–4가 새 #12 위로 restack됐고 diff는 그대로다"
   한 줄만 남습니다. 아무 뜻도 없는 "새 커밋" 세 줄 대신입니다.
3. 실제로 바뀐 레이어는 아직 게시하지 않은 지적을 새 diff에 다시 앵커합니다. 더 이상 풀리지 않는
   앵커는 버리지 않고 전반 지적으로 강등합니다. 게시된 코멘트는 GitHub의 outdated 표시에 맡깁니다
   (지금 폴링이 이미 읽고 있습니다).
4. 병합된 레이어는 `merged`로 표시되고, 폴링과 재조회에서 빠집니다. 그 지적과 게시한 코멘트는
   기록으로 남습니다.

후속 턴 프롬프트는 기존 "리뷰 이후 무슨 일이 있었나" 위에 어느 레이어가 바뀌었고, 어느 것이 그저
restack됐고, 어느 것이 병합됐는지를 적습니다. diff는 여전히 다시 보내지 않습니다 — 대화를 resume
하므로 모델은 이미 갖고 있고, 다시 보내면 컨텍스트만 태우며 앞선 판단을 흔듭니다.

### 어디서 시작하는가

둘 다입니다. 서로 다른 질문에 답하기 때문입니다.

**시작 모달**(`PrReviewStartModal`) — "PR 번호가 있다". PR을 고르면 `stackResolve`가 그것이 스택에
속하는지 봅니다. 속하면 모달이 레이어 목록과 함께 "스택 전체를 리뷰" 체크박스를 **기본 켬**으로
보여 줍니다. 기본을 켜 두는 것은 의도한 선택입니다 — 스택의 한 층만 따로 보는 것이 지금 잘못돼 있는
바로 그 지점이고, 5개짜리 스택의 가운데 PR 주소를 붙여 넣은 사람이 나머지 넷을 무시하기로 정했을 리는
거의 없습니다. 레이어 목록과 규모(`5 PRs · 62 files`)가 시작 전에 보이고, 끄는 것은 한 번입니다.

**`StackPopover`** — "스택을 보고 있다". 이 팝오버는 이미 두 스택 모델을 한 줄 목록으로 정규화해
두었습니다. 맨 위의 **Review stack** 액션이 그 목록에서 PR이 있는 행들로 리뷰를 시작하고, 없는 행이
있으면 그렇다고 말합니다.

둘 다 같은 `startReview({ repoId, prNumbers, … })`를 부릅니다. 매니저에 별도의 "스택 리뷰" 입구는
없습니다.

## 데이터 모델 변경

| 타입 | 변경 |
| --- | --- |
| `ReviewSession` | PR 단위 필드 제거, `layers: ReviewLayer[]`(아래→위)와 `truncatedFiles: number` 추가 |
| `ReviewLayer` | 신규. PR 단위 GitHub 상태: PR 메타, `headSha`, 워터마크, `summary`, `lastSubmission`, `merged` |
| `ReviewAnchor` | `prNumber: number` 추가 — 필수 |
| `ReviewFinding` | `prNumber?: number`, `stackPrNumbers?: number[]` 추가 |
| `ReviewFindingInput` | `prNumber?: number` 추가 |
| `ReviewArtifact` | `layers: { prNumber, summary }[]`, `stack: ReviewFindingInput[]` 추가 |
| `PostedComment` | `prNumber?: number` 추가 — 답글과 outdated 판정을 라우팅한다 |
| `ReviewActivityItem` | 답글·커밋 항목에 `prNumber?: number`, `restack` 종류 추가 |
| `ReviewLayerDiff` | 신규: `{ prNumber, diff: ReviewDiff }`. `ReviewDiff` 자체는 그대로 |
| `ReviewBundle` | `diff: ReviewDiff \| null` → `diffs: ReviewLayerDiff[]` |

선택 필드가 선택인 이유는 옛 레코드에 없기 때문이고, 읽는 쪽은 값이 없으면 "세션의 유일한 레이어"로
해석합니다. `ReviewDiff`·`ReviewHunk`·`ReviewFileDiff`·`DiffRow`는 손대지 않습니다 — PR 하나를
파싱하는 코드는 정확하고 테스트도 그쪽에 있습니다. 여러 PR 지원은 그 위를 감싸는 그릇이지 파서의
변경이 아닙니다.

사이드카 저장은 append 기반 last-write-wins JSONL 그대로입니다. diff 레코드에 PR 번호가 붙고 id가
고정 `__diff__`에서 `__diff__:<prNumber>`로 바뀌어, 레이어를 다시 받을 때 그 레이어만 덮어씁니다.
옛 id로 쓰인 레코드는 유일한 레이어의 diff로 읽힙니다.

리뷰 워크트리는 레이어마다가 아니라 **맨 위 레이어 하나**입니다. 모든 레이어의 head는 한 번의
`git fetch`로 `refs/wooi/review/<reviewId>/pr-<n>`에 들어가므로, 에이전트가 체크아웃을 N번 하지 않고도
어느 레이어든 `git diff <base-ref>...<head-ref>`나 `git show <ref>:<path>`로 볼 수 있습니다 —
"레이어 3이 건드리기 전에 이 파일이 어땠나"가 필요로 하는 것이 바로 그것입니다. 워크트리를 N개 만들면
디스크가 N배가 되고 "그 파일을 읽어라"가 어느 트리를 뜻하는지 모호해집니다. 삭제는
`refs/wooi/review/<reviewId>/` 네임스페이스를 통째로 지우고, 아카이브는 지금과 같은 이유로 남깁니다.

## 프롬프트 전략

사용자의 프롬프트가 맨 앞에 그대로 옵니다 — 그것이 리뷰의 주제를 정하고, 아래 규약은 답의 모양만
정합니다. 그다음 순서대로.

1. **스택 맥락.** 위에서 말한 골격: 정렬된 레이어, 레이어 교차 파일 표, 레이어별 로컬 ref 이름,
   그리고 잘린 파일.
2. **스택 질문들.** 산출물로 세우고 하나씩(순서·독립성·무효화·알갱이 크기·되돌림) 이름을 붙이며,
   PR을 따로따로 리뷰하는 것은 이 작업이 아니라는 것과, 그 층을 혼자 리뷰해도 똑같이 나올 지적은
   `stack`이 아니라 `inline`에 간다는 것을 명시합니다.
3. **앵커 규칙.** `prNumber`가 앵커의 일부가 되었고 추측이 아니라 파일 헤더에서 옮겨 적는다는 점
   말고는 그대로입니다.
4. **출력 계약.** 기존 구조화 출력 스키마(`outputFormat: { type: 'json_schema' }`, CLI가 스키마
   위반을 스스로 재시도)에 `stack`과 `layers`가 붙고 `inline` 항목의 `prNumber`가 필수가 됩니다.
   nullable union은 계속 쓰지 않습니다 — 선택은 `required`에서 빼는 것으로만 표현합니다. 일부 스키마
   강제 구현이 `["integer","null"]`을 거부합니다.
5. **diff.** 레이어별로, 파일 헤더마다 PR 번호를 달고.

단일 PR 리뷰는 레이어 하나로 같은 프롬프트를 렌더합니다. 레이어가 하나면 스택 절이 통째로 빠지므로
프롬프트 빌더는 하나뿐이고, 드문 스택 리뷰가 아니라 매일 도는 단일 PR 리뷰가 그 코드를 검증합니다.

## 구현 순서

1. **공유 타입과 스택 해석.** `ReviewLayer`·`ReviewLayerDiff`, 앵커·지적 필드,
   `stackHead()`/`layerFor()` 헬퍼, `StackPopover`에서 꺼낸 `workspaceStackMembers()`,
   `stackResolve.ts`, 스키마 마이그레이션 v21과 `normalizeShape`. 테스트: 두 모델과
   `buildStackFromPrs`를 통한 스택 해석, v20 단일 PR 리뷰의 마이그레이션.
2. **리뷰 엔진.** 멀티 ref 워크트리, `resolveStackAnchor`와 강등 규칙, diff 배분과 잘림 보고,
   프롬프트와 스키마, 레이어 위의 `buildFindings`, 매니저 일반화 — 시작, 게시 라우팅, 레이어별 제출,
   레이어별 폴링, restack 감지, 후속 턴. 테스트: 앵커링(모호한 경로, 틀린 레이어 `prNumber`,
   레이어 안 스냅), 배분과 잘림, restack 감지.
3. **렌더러.** 파일 목록과 diff 뷰의 레이어 묶기, 스택 지적 구역, 레이어별 제출 모달, 활동의 레이어
   라벨, 시작 모달의 스택 선택지, `StackPopover` 입구.

셋은 함께 나갑니다. 쪼개는 안은 검토했고 타입을 쓰고 나서 접었습니다 — 앵커의 `prNumber`, 지적의
`prNumber`, "봤음" 키의 `prNumber`는 하나의 설계 결정이고 렌더러가 셋 다 읽습니다. 필드 선언만 든
첫 PR, 그것에 의미를 주는 둘째, 그것을 보이게 하는 셋째는 따로 판단할 수 없는 세 개의 PR이고,
그것이야말로 이 기능이 잡아내려는 실패입니다.
