# 내장 MCP 서버

[English](./built-in-mcp.md) · **한국어**

Wooi 는 모든 코딩 에이전트 세션에 `wooi` 라는 내장 MCP 서버를 제공합니다. 에이전트는 이 서버의
도구로 대화 안에서 워크스페이스, stacked PR, 리포 스크립트, GitHub 이슈, 선택적 서브에이전트를
조율할 수 있습니다.

별도 설치나 설정은 필요하지 않습니다. Wooi 가 시작한 Claude Code·Codex 세션에 자동으로
연결됩니다. 다른 MCP 클라이언트에서 접속하는 원격 서버가 아니라 앱 내부 서버입니다.

## 도구 이름과 제공 조건

도구는 보통 에이전트에게 `mcp__wooi__<도구-이름>` 으로 보입니다. 대부분의 도구 정의는 필요할 때
불러오므로, 처음 모델 컨텍스트에 보이지 않아도 도구 검색을 통해 사용할 수 있습니다.

핵심 도구 15개는 모든 워크스페이스에 제공됩니다. `claude_subagent` 와 `codex_subagent` 는
멀티 에이전트 모드를 켜고 해당 백엔드에 위임할 수 있을 때만 추가됩니다.

## 안전 모델

- 대부분의 도구는 호출한 워크스페이스 자체에 작용합니다. 에이전트가 호출자 워크스페이스를 다른
  값으로 바꿀 수 없습니다.
- 대상 `workspaceId` 를 받는 도구는 호출한 워크스페이스가 직접 만든 워크스페이스만 대상으로 삼을
  수 있습니다. `archive_workspace` 는 호출자 자신을 아카이브할 수 없고, `notify_child` 는 바로
  아래의 stacked 자식으로 더 제한됩니다.
- `send_to_workspace` 만 예외인데, 경계를 없애는 것이 아니라 옮깁니다. 리포를 가리지 않고 열려
  있는 아무 워크스페이스나 지목할 수 있는 대신, 전달할지는 **받는 쪽**이 정합니다.
  [Peer 메시지](#peer-메시지)를 참고하세요.
- 읽기 전용 도구는 승인 없이 실행됩니다. 상태를 바꾸는 도구는 워크스페이스 권한 모드를 따르며,
  보통 실행 전에 승인 카드를 표시합니다. Full Access 에서는 승인 없이 실행합니다.
- Claude 인프로세스 서버는 세션에서 호출자를 압니다. Codex 전송 계층은 Wooi 가 그 스레드의 도구
  서버에 내려 준 환경변수에서 호출자를 읽습니다. 모델은 자기가 어느 워크스페이스인지 말하지 않고,
  다른 워크스페이스를 주장할 수도 없습니다. 그래도 Wooi 는 현재 턴이 돌고 있지 않은 호출자를
  거부합니다. 어떤 도구 스키마에도 전송용 인자를 덧붙이지 않으므로, `workspaceId` 인자는 언제나
  "그 도구가 작용할 대상" 을 뜻합니다.
- 도구 실패는 읽을 수 있는 MCP 오류로 에이전트에게 돌아가므로 요청을 고쳐 재시도할 수 있습니다.

## 워크스페이스 도구

### `create_workspace`

리포 기본 브랜치에서 독립 워크스페이스를 만듭니다.

| 입력 | 타입 | 필수 | 설명 |
| --- | --- | --- | --- |
| `name` | string | 아니요 | 브랜치 이름. 생략하면 Wooi 가 생성합니다. |
| `task` | string | 아니요 | 새 워크스페이스의 첫 메시지. 주면 즉시 턴을 시작합니다. |

새 워크스페이스는 스택 부모가 없고, 호출자에게 보고하지 않으며, `check_stacked_work` 에 나타나지
않습니다. 원격 기본 브랜치에서 시작하므로 호출자의 미커밋 변경은 생성에 영향을 주지 않습니다.

### `create_stacked_workspace`

현재 브랜치의 커밋된 tip 에서 바로 아래 자식 워크스페이스를 만듭니다. 자식 PR 은 현재 브랜치를
base 로 삼습니다.

| 입력 | 타입 | 필수 | 설명 |
| --- | --- | --- | --- |
| `name` | string | 아니요 | 브랜치 이름. 생략하면 Wooi 가 생성합니다. |
| `task` | string | 아니요 | 자식에게 보낼 완전한 인계 메시지. 주면 즉시 턴을 시작합니다. |

현재 worktree 가 깨끗해야 합니다. 방금 끝낸 작업에서 자식이 확실하게 시작할 수 있도록 먼저 변경을
커밋해야 합니다.

### `archive_workspace`

호출자가 만든 워크스페이스를 아카이브하고 worktree 를 제거합니다.

| 입력 | 타입 | 필수 | 설명 |
| --- | --- | --- | --- |
| `workspaceId` | string | 예 | 생성 결과 또는 워크스페이스 조회 도구에서 받은 ID. |

대상은 실행 중인 턴이 없어야 하며 미커밋 변경도 없어야 합니다. 브랜치, PR, 대화는 보존되므로
사용자가 사이드바에서 복원할 수 있습니다.

### `check_related_work`

같은 리포에 열린 부모, 자식, 무관한 형제 워크스페이스를 나열합니다. 결과에는 diff 가 아닌 변경
경로만 담기며, 호출자의 경로와 겹치는 부분을 계산합니다.

| 입력 | 타입 | 필수 | 설명 |
| --- | --- | --- | --- |
| `paths` | string[] | 아니요 | 변경할 리포 상대 경로. 생략하면 호출자가 이미 변경한 경로를 사용합니다. |

각 결과에는 관계, 실행 상태, 브랜치, 호출자가 만든 워크스페이스인지가 표시됩니다. 결과는
워크스페이스 20개, 워크스페이스당 경로 50개로 제한하며 겹침이 있는 항목을 우선합니다.
`note` 에는 겹침 여부를 문장으로 담아, 겹칠 때는 편집 전에 사용자에게 알리도록 안내합니다.

이 도구는 정의를 항상 시스템 프롬프트에 싣습니다(`alwaysLoad`). 다른 도구처럼 검색으로 찾게 두면
겹침의 존재를 모르는 에이전트에게는 검색할 단어가 없어, 정작 필요한 순간에 호출되지 않습니다.

## Stacked 워크스페이스 조율

### `check_stacked_work`

바로 아래 자식 워크스페이스와 각 브랜치, 실행·PR 상태, 호출자가 만들었는지, 자식의 마지막 보고를
나열합니다. 입력이 없는 읽기 전용 도구입니다.

보고는 부모 에이전트 컨텍스트에 자동으로 들어오지 않습니다. 자식 결과가 다음 행동에 영향을 줄 때나
`notify_child` 를 사용하기 전에 이 도구를 호출합니다.

### `report_to_parent`

이 워크스페이스가 쌓인 부모 워크스페이스에 결과를 기록합니다.

| 입력 | 타입 | 필수 | 설명 |
| --- | --- | --- | --- |
| `summary` | string | 예 | 완료한 작업, 결정 또는 막힌 이유를 독립적으로 이해할 수 있게 쓴 설명. |
| `status` | `done` \| `blocked` | 아니요 | 기본값은 `done`. |

보고는 부모를 방해하거나 부모의 턴을 시작하지 않습니다. 나중에 다시 보고하면 앞선 보고를
대체합니다. 독립 워크스페이스에는 부모가 없으므로 이 도구를 성공적으로 쓸 수 없습니다.

### `notify_child`

호출자가 직접 만든 stacked 자식에게 메시지를 보냅니다.

| 입력 | 타입 | 필수 | 설명 |
| --- | --- | --- | --- |
| `workspaceId` | string | 예 | `check_stacked_work` 에서 얻은 자식 ID. |
| `message` | string | 예 | 무엇이 바뀌었고 자식이 어떻게 대응해야 하는지 독립적으로 이해할 수 있게 쓴 메시지. |

보고와 달리 자식의 턴을 시작합니다. 자식이 실행 중이면 현재 턴 뒤에 메시지를 대기시킵니다.

## Peer 메시지

Stacked 조율은 한 축으로만 흐릅니다. 부모가 자식을 깨우고, 자식은 기록만 남깁니다. Peer
메시지는 다른 축입니다. 열려 있는 워크스페이스는 다른 어떤 워크스페이스에도 짧은 평문 메시지를
보낼 수 있습니다. 리포가 달라도, 자기가 만들지 않은 워크스페이스여도 됩니다.

건너가는 것은 텍스트뿐입니다. 대화 기록·파일·diff 는 넘어가지 않습니다.

### 수신 정책

발신이 열려 있으므로 경계는 받는 쪽에 둡니다. 워크스페이스마다 수신 정책이 있고, 사이드바 행
메뉴에서 바꿉니다.

| 정책 | 동작 |
| --- | --- |
| `hold`(기본) | Wooi 가 메시지를 붙잡고 승인 배너를 띄웁니다. 전달하기 전에는 에이전트에게 아무것도 가지 않습니다. |
| `accept` | 곧바로 전달합니다. 그 워크스페이스에서 턴이 시작됩니다. |
| `refuse` | 받지 않고, 보낸 쪽에 거절을 알립니다. |

기본값이 `hold` 인 이유는 비용입니다. 전달은 곧 받는 워크스페이스에서 도는 유료 턴이고, 그
승인은 다른 워크스페이스의 에이전트가 아니라 사용자가 해야 합니다. 대기 중인 메시지를 거절하면
그대로 사라지며, 보낸 쪽에는 알리지 않습니다.

예외가 하나 있습니다. **자기가 만든** 워크스페이스에는 곧바로 전달합니다. 생성 도구 호출을
승인할 때 그 관계를 이미 승인했기 때문입니다. `refuse` 는 이 예외까지 이깁니다.
`notify_child` 도 같은 규칙을 따릅니다.

같은 대상에게 1분 안에 똑같은 메시지를 다시 보내면 두 번째는 버립니다. 워크스페이스 한 곳이
대기시킬 수 있는 메시지는 최대 20건이고, 넘으면 오래된 것부터 버립니다.

### `list_workspace_peers`

호출자를 뺀 모든 열린 워크스페이스를 리포를 가로질러 나열합니다. 브랜치·리포·실행 여부와 함께,
메시지가 곧바로 도착할지 승인을 기다릴지도 알려 줍니다. 입력이 없고 읽기 전용입니다. 결과는
30개로 제한하며 같은 리포를 앞에 놓습니다.

### `send_to_workspace`

열려 있는 다른 워크스페이스에 평문 메시지를 보냅니다.

| 입력 | 타입 | 필수 | 설명 |
| --- | --- | --- | --- |
| `targetWorkspaceId` | string | 예 | `list_workspace_peers` 에서 얻은 수신자 ID. 자기 자신은 넣지 않습니다 — 호출자는 Wooi 가 이미 압니다. |
| `message` | string | 예 | 무엇이 바뀌었고 상대가 무엇을 달리해야 하는지 독립적으로 이해할 수 있게 쓴 텍스트. |

Wooi 는 전달 전에 출처 문단을 씌웁니다. 받는 에이전트가 사용자의 새 지시가 아니라 다른
워크스페이스에서 온 소식으로 읽게 하기 위해서입니다. 이 문단은 메시지에 아무 권한이 없다는
것도 함께 밝힙니다. 승인을 대신할 수 없고, 다른 워크스페이스가 요구했다는 이유로 설정이나 프로젝트
지침을 고쳐서도 안 됩니다.

결과에는 전달됐는지 대기 중인지가 담깁니다. 대기 중인 메시지는 영영 도착하지 않을 수도 있으므로,
에이전트는 답을 기다리며 멈춰서는 안 됩니다.

### Wooi 밖의 세션

Claude Code 2.1.224+ 부터 같은 머신의 세션끼리 직접 메시지를 주고받습니다. Wooi 워크스페이스도
그런 세션이므로, 이 통로를 기본값에 맡기지 않고 Wooi 가 설정합니다.

- 워크스페이스마다 `wooi/<리포>/<브랜치>` 로 자기를 알립니다. 터미널에서 `/list-agents` 를 쳤을 때
  랜덤 워크트리 이름 대신 무슨 작업인지 읽히게 하기 위해서입니다.
- 네이티브 수신은 같은 워크스페이스 정책을 따르되 두 값으로 접힙니다. `accept` 는 그대로고,
  `hold` 와 `refuse` 는 둘 다 `refuse` 가 됩니다. 앱 밖에서 오는 메시지는 Wooi 가 붙잡아 둘 수
  없습니다. 승인 다이얼로그는 터미널 UI 의 것이라 앱이 띄우는 세션은 그릴 방법이 없습니다.
  그래서 "승인을 받고 싶다" 는 곧 "승인 없이 들어오게 두지 않는다" 로 읽습니다. 덕분에 뻔한
  우회로도 함께 막힙니다. Wooi 워크스페이스는 네이티브 `SendMessage` 로도 닿지만, 대기 정책인
  워크스페이스는 그쪽에서도 거절하므로 두 경로가 하나의 정책으로 수렴합니다.
- 이 머신 밖으로 나가는 메시지는 승인을 요구합니다(`isolatePeerMachines`). 머신 간 전달은
  Anthropic 서버를 거치지만 같은 머신은 그렇지 않기 때문입니다.
- 실제로 도착한 네이티브 메시지는 발신자와 함께 대화에 기록됩니다. 기록하지 않으면 모델에게는
  전달되는데 화면에는 아무것도 남지 않아, 에이전트가 난데없이 방향을 튼 것처럼 보입니다.

에이전트는 다른 Wooi 워크스페이스에는 `send_to_workspace` 를, 앱 밖 세션에는 기본 제공
`SendMessage` 를 씁니다. Codex 에는 대응하는 네이티브 기능이 없으며, Wooi 도구가 두 백엔드
모두에 존재하는 이유가 그것입니다.

## Pull request와 GitHub 이슈

### `open_pull_request`

현재 브랜치의 PR 을 열며, 필요하면 먼저 브랜치를 push 합니다.

| 입력 | 타입 | 필수 | 설명 |
| --- | --- | --- | --- |
| `title` | string | 예 | PR 제목. |
| `body` | string | 예 | Markdown 형식의 PR 설명. |
| `draft` | boolean | 아니요 | Draft 생성 여부. 기본값은 `false`. |

Wooi 가 base 를 자동으로 고릅니다. stacked 워크스페이스는 부모 브랜치, 그 외에는 리포 기본
브랜치입니다. 브랜치에는 base 에 없는 커밋이 하나 이상 있어야 합니다. 열린 PR 이 이미 있으면 새로
만들지 않고 기존 PR 을 반환합니다.

### `list_issues`

현재 리포의 열린 GitHub 이슈를 번호, 제목, 작성자, 라벨, URL 과 함께 나열합니다. 읽기 전용이며
워크스페이스를 만들지는 않습니다.

| 입력 | 타입 | 필수 | 설명 |
| --- | --- | --- | --- |
| `limit` | integer | 아니요 | 최대 이슈 수. 기본값 30, 최댓값 100. |

이슈 작업을 시작하려면 별도로 `create_workspace` 를 호출하고, 새 에이전트에 필요한 이슈 정보를
`task` 에 모두 넣어야 합니다.

## 리포 스크립트

스크립트 이름은 리포 설정에서 가져옵니다. 예약 이름 `setup` 은 setup 스크립트를 가리킵니다.
잘못된 이름을 주면 사용 가능한 이름을 오류로 돌려줍니다.

### `run_script`

설정된 스크립트를 백그라운드에서 시작합니다. 이미 실행 중이면 재시작합니다. 프로세스는 에이전트
턴이 끝나도 계속 실행되고 사용자가 보는 것과 같은 스크립트 패널에 출력합니다.

| 입력 | 타입 | 필수 | 설명 |
| --- | --- | --- | --- |
| `name` | string | 예 | 설정된 스크립트 이름 또는 `setup`. |

### `stop_script`

실행 중인 설정 스크립트를 중지합니다.

| 입력 | 타입 | 필수 | 설명 |
| --- | --- | --- | --- |
| `name` | string | 예 | 설정된 스크립트 이름 또는 `setup`. |

### `read_script_output`

최근 출력과 함께 실행 상태와 종료 코드를 반환합니다. 읽기 전용입니다.

| 입력 | 타입 | 필수 | 설명 |
| --- | --- | --- | --- |
| `name` | string | 예 | 설정된 스크립트 이름 또는 `setup`. |
| `tailLines` | integer | 아니요 | 반환할 마지막 줄 수. 기본값 200, 최댓값 500. |

로그 끝부분을 보존하며 출력은 약 8 KiB 로 제한됩니다. 잘렸는지도 결과에 표시합니다.

## 에이전트 팀 모드

### `switch_to_agent_team`

Solo 워크스페이스를 에이전트 팀으로 바꿉니다. 아래의 서브에이전트 도구가 존재하게 만드는 것이
이 도구입니다. Solo 로 만든 워크스페이스에서 사용자가 "여러 에이전트로 나눠서 해 달라" 고 명시적으로
요청할 때 사용합니다.

| 입력 | 타입 | 필수 | 설명 |
| --- | --- | --- | --- |
| `reason` | string | 예 | 무엇을 어느 에이전트에게 위임하려는지 한 문장. 승인 카드에 표시됩니다. |

전환은 한 방향입니다. Solo 로 되돌리는 도구는 두지 않았습니다 — 아무도 요청하지 않은 능력 축소를
모델이 스스로 하게 둘 이유가 없기 때문입니다. 되돌리는 것은 대화 헤더의 배지로 사용자가 합니다.

서브에이전트 도구는 세션을 열 때 그 세션에 묶이므로, 호출한 턴에는 아직 나타나지 않습니다. Wooi 는
그 턴이 끝나는 즉시 세션을 다시 열고 같은 대화를 이어받아 스스로 다음 턴을 시작하므로, 도구는 바로
그다음 턴부터 쓸 수 있습니다. 사용자가 다시 말을 걸 필요는 없습니다 — 여기까지 온 계기가 사용자의
요청이고, 이어지는 턴이 곧 그 요청이기 때문입니다. 도구 결과가 이 사실을 알려 주며, 호출한
에이전트는 턴을 마치고 그다음 턴에서 위임해야 합니다.

이미 팀인 워크스페이스에서 부르면 아무것도 바뀌지 않고 세션도 다시 열지 않습니다. 워크스페이스의
메인 에이전트가 팀을 이끌 수 없으면 호출이 실패합니다 — 전환해 봐야 쓸 수 있는 팀원이 없기 때문입니다.

## 선택적 서브에이전트 도구

멀티 에이전트 모드에서 위임이 가능하면 백엔드별 도구가 하나씩 나타납니다.

- `claude_subagent`
- `codex_subagent`

각 도구는 같은 worktree 에서 서브에이전트를 시작하고 최종 텍스트 결과 하나를 기다립니다. 부모
워크스페이스의 권한 모드를 사용합니다. 서브에이전트는 빈 대화 컨텍스트로 시작하며 실행 중 질문을
돌려보낼 수 없습니다.

| 입력 | 타입 | 필수 | 설명 |
| --- | --- | --- | --- |
| `description` | string | 예 | 실행 중 표시할 3~6단어의 짧은 라벨. |
| `prompt` | string | 예 | 파일, 제약, 기대 결과를 모두 담은 완전한 작업 설명. |

Claude 는 Wooi 서브에이전트 도구 여러 개를 동시에 시작할 수 있습니다. 현재 Codex 는 MCP 도구
호출을 직렬화하므로 위임 여러 건이 차례로 완료됩니다.

## 슬래시 명령

각 도구에는 슬래시 명령도 있습니다. 에이전트가 스스로 호출하기를 기다리지 않고 직접 부를 수
있습니다. 명령은 플러그인 이름으로 네임스페이스가 붙어 사용자의 기존 명령과 겹치지 않습니다 —
`/wooi:pr`, `/wooi:children` 같은 형태입니다. 카탈로그는 `src/shared/wooiCommands.ts` 입니다.

| 명령 | 도구 | 실행 방식 |
| --- | --- | --- |
| `/wooi:pr [추가 지시]` | `open_pull_request` | 에이전트 |
| `/wooi:new <할 일>` | `create_workspace` | 에이전트 |
| `/wooi:stack <할 일>` | `create_stacked_workspace` | 에이전트 |
| `/wooi:report [보고 내용]` | `report_to_parent` | 에이전트 |
| `/wooi:notify <바뀐 것>` | `notify_child` | 에이전트 |
| `/wooi:send <바뀐 것>` | `send_to_workspace` | 에이전트 |
| `/wooi:team [위임할 일]` | `switch_to_agent_team` | 에이전트 |
| `/wooi:peers` | `list_workspace_peers` | 즉시 |
| `/wooi:children` | `check_stacked_work` | 즉시 |
| `/wooi:related [경로…]` | `check_related_work` | 즉시 |
| `/wooi:issues [개수]` | `list_issues` | 즉시 |
| `/wooi:run <이름>` | `run_script` | 즉시 |
| `/wooi:stop <이름>` | `stop_script` | 즉시 |
| `/wooi:logs <이름> [줄 수]` | `read_script_output` | 즉시 |
| `/wooi:archive <워크스페이스 id>` | `archive_workspace` | 즉시 |

team 모드 워크스페이스에서는 에이전트 종류마다 커맨드가 하나씩 더 생깁니다 — `/wooi:claude`,
`/wooi:codex` 로, `claude_subagent`·`codex_subagent` 도구에 대응합니다. `<할 일>` 을 받아
에이전트에게 넘기고, 완전한 브리프는 에이전트가 씁니다. team 모드 밖에서는 도구 자체가 없으므로
이 커맨드도 뜨지 않습니다.

**즉시** 명령은 메인 프로세스에서 도구를 그대로 실행하고 결과를 카드로 보여 줍니다. 턴도 토큰도
쓰지 않고, 승인 카드도 뜨지 않습니다 — 사용자가 직접 이름을 쳐서 부른 것이라 확인할 것이 없기
때문입니다. 위 표에 있는 명령만 이 경로로 실행되고, 인자도 파서를 통과한 것만 도구에 닿습니다.

**에이전트** 명령은 요청을 에이전트에게 넘깁니다. 인자가 대화 맥락을 읽어야 쓸 수 있는 산문이기
때문입니다 — PR 본문, 인계문, 보고서가 그렇습니다. 명령은 "이 도구를 부르라"는 프롬프트로
확장됩니다.

### 백엔드별 처리

Wooi 는 시작할 때 카탈로그에서 Claude Code 플러그인을 만들어 `userData` 아래에 씁니다
(`src/main/agent/plugin.ts`). 이 플러그인은 `skipMcpDiscovery` 와 함께 세션에 전달됩니다 —
`wooi` MCP 서버는 Wooi 가 이미 인프로세스로 제공하기 때문입니다. 그 뒤로는 Claude Code 가
자동완성 항목과 프롬프트 확장을 모두 맡으므로, 명령 목록을 어디에도 하드코딩하지 않습니다.

위임 커맨드가 든 변형과 없는 변형 두 개를 만들어 두고 세션의 모드에 맞는 쪽을 물립니다. 하나로
합칠 수는 없습니다 — 플러그인 이름이 곧 커맨드 접두사라 둘 다 `wooi` 여야 하고, 한 세션은 그중
하나만 물 수 있기 때문입니다.

Codex 는 같은 플러그인 포맷을 읽지만 슬래시 명령 처리가 TUI 쪽에 있고, Wooi 가 사용하는
app-server 프로토콜에는 명령을 나열하거나 확장하는 RPC 가 없습니다. 그래서 Codex 에서는 Wooi 가
자동완성 항목을 직접 싣고 프롬프트도 직접 확장합니다(`src/main/codex/manager.ts`). 즉시 명령은
입력창에서 가로채므로 두 백엔드에서 동일하게 동작합니다.

## 구현 위치

도구 카탈로그와 스키마는 `src/main/agent/tools/catalog.ts`, 핸들러 등록은
`src/main/agent/tools/index.ts` 에 있습니다. Claude 는 `src/main/claude/wooiMcp.ts` 의 인프로세스
어댑터를, Codex 는 `src/main/codex/toolShim.ts` 의 stdio 어댑터를 사용합니다. 두 전송 계층 모두
실행을 같은 registry 와 `src/main/agent/tools/` 아래 핸들러로 전달합니다.

슬래시 명령 카탈로그는 `src/shared/wooiCommands.ts`, 생성되는 Claude 플러그인은
`src/main/agent/plugin.ts`, 즉시 실행은 `src/main/ipc.ts` 의 `command:wooiRun` 핸들러가 맡습니다.
