# 버전 · 릴리스 정책

[English](./releasing.md) · **한국어**

Wooi 가 버전 번호를 어떻게 정하고, 언제 릴리스를 자르고, 어떻게 배포하는지를 정리한
문서다. 판단 규칙만 필요하면 [§2](#2-어느-자리를-올릴까) 만 보면 된다.

---

## 1. 버전 형식

Wooi 는 **SemVer 문법에 사용자 관점 의미를 부여**해서 쓴다.

```
MAJOR . MINOR . PATCH
```

Wooi 는 라이브러리가 아니라 최종 사용자용 데스크톱 앱이다. API 를 두고 컴파일하는
하위 코드가 없으니 고전적 SemVer 의 "호환성 깨짐" 정의가 그대로 맞아떨어지지 않는다.
그래서 각 자리를 **앱을 쓰는 사람 입장에서 무엇을 뜻하는가**로 정의한다.

| 자리 | 의미 | 올리는 경우 |
|---|---|---|
| **MAJOR** | 뭔가를 다시 배우거나, 손으로 조치해야 한다 | 세션·설정 데이터가 비호환으로 마이그레이션될 때 · 최소 요구사항 변경(지원 macOS 버전, 필수 외부 도구) · 핵심 워크플로 개편으로 기존 사용법이 더는 통하지 않을 때 |
| **MINOR** | 새로운 게 생겼다 | 사용자 눈에 보이는 기능·UX 변화 |
| **PATCH** | 같은 앱, 문제만 줄었다 | 버그 수정, 성능, 내부 구현 |

MAJOR 는 한동안 `1` 에 머무를 것으로 본다. 정책을 안 지키는 게 아니라 의도한
동작이다 — VS Code 는 10년째 `1.x` 를 내고 있다.

`package.json` 의 version 이 단일 진실 원천이다. `app.getVersion()`, DMG,
`latest-mac.yml`, git 태그가 전부 여기서 파생된다.

## 2. 어느 자리를 올릴까

> **규칙:** 이번 릴리스에 들어가는 커밋을 전부 훑는다.
>
> - `feat!:` 또는 `BREAKING CHANGE:` 푸터가 있으면 → **MAJOR**
> - 아니고 `feat:` / `feat(scope):` 가 하나라도 있으면 → **MINOR**
> - 그 외 → **PATCH**

일부러 기계적으로 만든 규칙이다. 버전 번호는 재량이 개입하는 순간 정보 전달을
멈추고, 실패 양상은 늘 같다. 전부 조용히 PATCH 가 된다.

```bash
# 다음 릴리스 범위의 커밋 목록.
git log --oneline $(git describe --tags --abbrev=0)..main
```

`docs:`, `ci:`, `chore:`, `style:`, `test:`, `build:`, `refactor:`, `perf:` 는
모두 PATCH 로 친다. 다만 이것들만으로는 **릴리스를 자를 이유가 되지 않는다**.
아래를 보라.

## 3. 언제 릴리스를 자르나

| 상황 | 조치 |
|---|---|
| `docs:` / `ci:` / `chore:` 만 쌓임 | **릴리스하지 않는다.** 배포 바이너리에 바뀐 게 없다. 랜딩 페이지는 GitHub Pages 로 따로 반영된다. |
| 의미 있는 `feat:` 가 하나 이상 쌓임 | **MINOR** 를 자른다. 주 1회 정도가 적당한 리듬이다. |
| 크래시 · 데이터 손실 · 업데이트 불가 버그 | 즉시 **PATCH** 를 자른다. |
| 우회 가능한 자잘한 `fix:` | 다음 MINOR 에 태워 보낸다. |

두 가지 제약이 이 리듬을 만든다. 공증은 빌드마다 Apple 서버 왕복으로 수 분이 걸리고,
릴리스는 매번 전 사용자에게 재시작을 요구한다. 하루 네 번 릴리스는 속도가 아니라
소음이다.

## 4. 버전 번호 불변

**GitHub Release 로 한 번 공개된 버전 번호는 재사용하지 않는다.** 잘못 나갔다면:

- 태그를 지우고 다시 밀지 **않는다**.
- 빌드를 재실행해 산출물을 덮어쓰지 **않는다**.
- 다음 PATCH 를 올려서 낸다.

이미 자동 업데이트를 받은 사용자는 옛 바이너리를 들고 있다. 같은 태그에 산출물만
갈아끼우면 같은 버전 번호를 보고하는 서로 다른 바이너리가 두 종류 돌아다니게 되고,
그 뒤로 들어오는 버그 리포트는 전부 검증이 불가능해진다.

`build.yml` 의 `--clobber` 경로는 **릴리스 객체는 만들어졌는데 산출물 업로드가
실패한**(예: 공증 실패) 경우의 복구 전용이다. 사용자가 이미 받은 릴리스를 다시
자르는 용도가 아니다.

## 5. Pre-release

지금은 쓰지 않지만 형식만 못 박아 둔다.

```
1.1.0-beta.1
```

유효한 SemVer 이고, `electron-updater` 의 정렬 기준에 맞으며, `allowPrerelease`
플래그 + GitHub pre-release 표시와 그대로 맞물린다. 형식을 지금 고정해 두면 나중에
베타 채널을 도입할 때 소급해서 이름을 바꿀 일이 없다. 채널 분리 자체는 현재 사용자
규모에서는 관리 비용이 더 크다.

## 6. 업데이트 알림 강도

릴리스는 **사용자가 설정을 열어 보지 않아도** 도달해야 한다. `src/main/updater.ts` 가
확인하고, 세 통로로 알린다.

**확인 시점** — 실행 8초 뒤 1회, 이후 2시간마다, 그리고 창 포커스·절전 복귀 때마다
(최소 30분 간격 스로틀). `setInterval` 은 맥이 잠들면 밀리므로 이벤트 트리거가 그
빈 구간을 메운다.

**알림 통로**

- **상단 배너** — 새 버전 발견(`available`)부터 뜬다. 닫아도 영구히 숨기지 않는다:
  상태·버전이 바뀌거나 8시간이 지나면 다시 뜬다. (며칠씩 켜 두는 앱이라, 한 번 닫으면
  영영 안 보이는 배너는 없는 것과 같다.)
- **OS 알림** — 창이 비활성일 때만. 다운로드 완료(`ready`) 시점에 한 번, 계속 무시하면
  24시간마다 한 번 더. 앱 밖에 있는 사용자에게 릴리스가 닿는 유일한 통로다.
- **타이틀바 점** — 설정 버튼 위의 상시 표시.

**읽기 전용 위치**(DMG 직접 실행 / App Translocation)에서도 확인은 계속한다. 자동
설치만 불가하므로 다운로드를 끄고 확인만 해서, "새 버전이 나왔다 + 수동으로 받아라"를
배너·OS 알림으로 똑같이 알린다. 이 경우가 사용자가 새 버전을 가장 놓치기 쉬운
상황이었다.

## 7. 릴리스 절차

1. **번호를 정한다** — [§2](#2-어느-자리를-올릴까).
2. **`release/vX.Y.Z` 브랜치**를 만들고 `package.json` 의 `version` 을 bump 한 뒤
   `npm install` 로 `package-lock.json` 을 따라오게 한다.
3. **`release: vX.Y.Z` 로 커밋**한다. 본문에는 이전 태그 이후의 사용자 눈에 보이는
   변경을 나열한다(나중에 메인테이너가 읽는 요약이 된다).
4. **`main` 에 병합**한다.
5. **병합 커밋에 태그를 달아 push** 한다.
   ```bash
   git checkout main && git pull
   git tag "v$(node -p "require('./package.json').version")"
   git push origin "v$(node -p "require('./package.json').version")"
   ```
   태그를 `package.json` 에서 파생시키면 아래의 불일치 사고를 원천 차단할 수 있다.
6. **나머지는 `build.yml` 이 한다** — 태그와 `package.json` 일치 검증, 서명 시크릿
   확인, 빌드·서명·공증, `codesign`/`stapler`/`spctl` 재검증, 그리고 자동 생성 노트로
   GitHub Release 생성.
7. **이어서 `homebrew-tap` 잡이 돈다** — 방금 올라간 `Wooi-arm64.dmg` 를 다시 받아
   해시를 계산하고, `build/homebrew/wooi.rb` 에 새 버전과 `sha256` 을 채워
   `youngminnnn/homebrew-tap` 의 `Casks/wooi.rb` 로 push 한다. 그래야
   `brew install --cask youngminnnn/tap/wooi` 가 새 빌드를 가리킨다. tap 저장소에
   `contents: write` 권한이 있는 PAT 를 `TAP_TOKEN` 시크릿으로 등록해야 하고,
   **없으면 조용히 넘어가지 않고 릴리스 실행을 실패시킨다** — brew 만 옛 버전에
   멈춰 있는 상태를 만들지 않기 위해서다.

### 불일치 가드

`electron-builder` 는 태그가 아니라 `package.json` 을 보고 빌드한다. `package.json`
bump 없이 `v1.1.0` 태그만 밀면 빌드는 **성공한다**. 대신 릴리스 제목만 `v1.1.0` 이고
바이너리와 `latest-mac.yml` 은 `1.0.4` 라서, 기존 사용자에게 업데이트가 영원히 가지
않는다. 설치 기반이 안 움직인다는 걸 누군가 눈치채기 전까지 아무 데서도 티가 안 난다.

`build.yml` 에 이 불일치를 공증 전에 잡아서 빌드를 실패시키는 preflight 스텝이 있다.
제거하지 말 것.

## 8. 향후 자동화 검토

[release-please](https://github.com/googleapis/release-please) 가 잘 맞는다. 이
저장소는 이미 Conventional Commits 형식의 PR 제목을 squash merge 하고 있고, 그게 정확히
release-please 의 입력이다. 도입하면 §2 를 통째로 넘길 수 있고(사람이 번호를 고르지
않는다), `CHANGELOG.md` 를 유지해 주며, 버전 bump PR 생성과 태그 push 까지 자동화된다.
위 절차 1~5 단계가 대체된다.

다만 §3 의 주 1회 리듬이 자리잡은 뒤에 붙이는 게 낫다. 자동화가 먼저 오면 지금의
습관이 봇에 그대로 굳는다.
