Comparison비교

Parallel worktrees are table stakes. The difference is what happens when work depends on work. 병렬 worktree 는 이제 기본이다. 갈리는 지점은 작업이 작업에 얹힐 때다.

Conductor, Vibe Kanban, Claude Squad, Crystal, Emdash, Orca and Wooi all do the same first thing: give every agent its own isolated git worktree so N tasks can run at once. That part is settled. This page compares what they do after that — and everything in the table below comes from each project's own documentation. Conductor, Vibe Kanban, Claude Squad, Crystal, Emdash, Orca, Wooi 는 첫 단계가 전부 같다. 에이전트마다 격리된 git worktree 를 주고 N 개 작업을 한꺼번에 돌린다. 거기까지는 이미 정리된 얘기다. 이 페이지는 그 다음을 비교한다. 아래 표의 내용은 전부 각 프로젝트의 공식 문서에서 확인한 것이다.

Three axes that actually separate them 실제로 갈리는 세 축

Run four agents on four unrelated bugs and any tool here will serve you well. The picture changes the moment task B needs task A's code before it can start. 서로 상관없는 버그 네 개에 에이전트 넷을 붙이는 일이라면, 여기 있는 어떤 도구를 써도 잘 굴러간다. 그림이 달라지는 건 B 작업이 A 작업의 코드 없이는 시작조차 못 하는 순간부터다.

Stacking. Can a new task branch off another task's branch instead of off main? Without it, task B either waits for A to merge, or starts from main and re-implements A's changes so its own diff makes sense. 스태킹. 새 작업을 main 이 아니라 다른 작업의 브랜치에서 딸 수 있는가? 이게 없으면 B 는 A 가 머지될 때까지 기다리거나, main 에서 시작해 A 의 변경을 다시 만들어 넣어야 자기 diff 가 말이 된다.

What happens on merge. Stacking is the easy half. The hard half is the parent merging: every child is now based on a commit that no longer exists on the target branch, and every child PR still points at a merged base. Someone has to rebase the children and retarget the PRs — either the tool, or you, by hand, in order, every time. 머지된 다음. 스택을 쌓는 건 쉬운 쪽이다. 어려운 쪽은 부모가 머지될 때다. 자식들은 이제 타깃 브랜치에 없는 커밋 위에 얹혀 있고, 자식 PR 은 전부 머지된 base 를 가리키고 있다. 누군가는 자식을 rebase 하고 PR base 를 다시 잡아야 한다. 도구가 하든지, 아니면 매번 사람이 순서대로 손으로 하든지.

Review, on the diff. Most tools here let you click a diff line and send a note to the agent that wrote it — a feedback loop for your own work. A separate question is whether you can pull up somebody else's open pull request and leave review comments that land on GitHub as review comments. diff 위에서 하는 리뷰. 여기 있는 도구 대부분은 diff 한 줄을 찍어 그걸 쓴 에이전트에게 메모를 보낼 수 있다. 내 작업을 다듬는 피드백 루프다. 그와는 별개로, 남이 열어 둔 pull request 를 불러와 GitHub 에 실제 리뷰 코멘트로 남길 수 있느냐는 또 다른 질문이다.

What each one is good at 각자 잘하는 것

These are all good tools built by people solving a real problem. They are not the same tool, and the right pick depends on which part of the problem is biting you. 여기 있는 건 전부 실제 문제를 풀려고 만든 좋은 도구다. 서로 같은 도구가 아니고, 지금 나를 물고 있는 문제가 무엇이냐에 따라 답이 달라진다.

Conductor

macOS

The tightest native loop around Claude Code, Codex and Cursor. Every task gets a workspace — branch, files, terminal, diff, review path — backed by a git worktree, and the diff viewer lets comments point at changed lines so the agent gets precise context instead of a paragraph of chat. If you want one polished Mac app and your tasks are independent, this is the shortest path. Claude Code, Codex, Cursor 를 감싸는 가장 매끄러운 네이티브 루프다. 작업마다 워크스페이스가 생기고 — 브랜치, 파일, 터미널, diff, 리뷰 경로까지 — 그 밑을 git worktree 가 받친다. diff 뷰어에서는 코멘트가 변경된 줄을 직접 가리켜서, 에이전트가 긴 채팅 대신 정확한 맥락을 받는다. 잘 다듬어진 맥 앱 하나면 되고 작업들이 서로 독립적이라면 이게 가장 빠른 길이다.

Vibe Kanban

Local web UI · npx로컬 웹 UI · npx

The one that treats planning as the bottleneck. A kanban board sits over the agents, issues break into sub-issues, and statuses move on their own when an agent picks work up. It creates worktrees and setup scripts for you, opens PRs with generated descriptions, and takes inline diff comments straight back to the agent. 병목을 계획 쪽으로 보는 도구다. 에이전트 위에 칸반 보드가 얹히고, 이슈는 하위 이슈로 쪼개지며, 에이전트가 일을 집어 들면 상태가 알아서 움직인다. worktree 와 셋업 스크립트를 대신 만들어 주고, 설명이 자동으로 붙은 PR 을 열고, diff 인라인 코멘트를 에이전트에게 곧장 돌려준다.

Claude Squad

Terminal · tmux + gh터미널 · tmux + gh

The lightest thing here, and deliberately so. One terminal window manages many agents — Claude Code, Codex, Gemini, Aider — each in its own worktree, running tasks in the background including auto-accept mode. Diff tab, review, commit, push. If you live in tmux and want nothing between you and the agents, it is hard to beat. 여기서 가장 가벼운 도구고, 일부러 그렇게 만들었다. 터미널 창 하나로 여러 에이전트 — Claude Code, Codex, Gemini, Aider — 를 각자의 worktree 에서 관리하고, 자동 수락 모드를 포함해 백그라운드로 작업을 돌린다. diff 탭, 리뷰, 커밋, push. tmux 안에서 살고 에이전트 사이에 아무것도 끼우고 싶지 않다면 이걸 이기기 어렵다.

Crystal

macOS · Electron

An early and influential take: run, inspect and test many Claude Code and Codex sessions side by side in worktrees, compare the approaches, then squash the winner and rebase it onto main from inside the app. Much of what the rest of this table takes for granted was normal here first. 초기에 나와서 영향을 크게 남긴 접근이다. 여러 Claude Code · Codex 세션을 worktree 안에서 나란히 돌리고 살펴보고 테스트한 뒤, 마음에 드는 쪽을 앱 안에서 squash 해 main 으로 rebase 한다. 이 표의 나머지가 당연하게 여기는 것 중 상당수가 여기서 먼저 당연해졌다.

Deprecated Feb 2026 — continues as Nimbalyst 2026년 2월 지원 종료 — Nimbalyst 로 이어짐

Emdash

macOS · Windows · Linux

The one that reaches furthest into the rest of your stack. Bring whichever CLI agent you already use, pull work in from Linear, GitHub, Jira, GitLab, Asana and more, run it locally or on a remote machine over SSH, then review diffs, open PRs and watch CI checks from one place. Open source, cross-platform, and moving fast. 개발 스택의 나머지 부분까지 가장 멀리 뻗는 도구다. 이미 쓰던 CLI 에이전트를 그대로 가져오고, Linear · GitHub · Jira · GitLab · Asana 등에서 할 일을 끌어오고, 로컬이든 SSH 로 붙은 원격 머신이든 거기서 돌린 다음, diff 리뷰와 PR 생성과 CI 체크 확인을 한 곳에서 한다. 오픈소스이고, 크로스 플랫폼이고, 빠르게 움직인다.

Orca

macOS · Windows · Linux · iOS · AndroidmacOS · Windows · Linux · iOS · Android

The widest surface area of the group. Fan a single prompt across five agents in five worktrees and merge the winner, drop comments on any diff line and ship them back, run worktrees over SSH, drive the whole thing from a CLI, and carry it in your pocket on iOS and Android. It is also the only other tool here whose docs name stacking directly — you can start a worktree from another local branch to stack on a PR that is still in review. 이 중에서 다루는 범위가 가장 넓다. 프롬프트 하나를 다섯 worktree 의 다섯 에이전트에 뿌려 놓고 이긴 쪽을 머지하고, diff 아무 줄에나 코멘트를 달아 돌려보내고, worktree 를 SSH 로 원격에서 돌리고, 전체를 CLI 로 조종하고, iOS · Android 로 들고 다닌다. 여기서 문서에 스태킹을 직접 언급하는 유일한 다른 도구이기도 하다 — 아직 리뷰 중인 PR 위에 얹으려고 다른 로컬 브랜치에서 worktree 를 시작할 수 있다.

Wooi

macOS · Claude Code + CodexmacOS · Claude Code + Codex

Same starting point as everyone else — one worktree, one branch, one agent per task, running in parallel. What Wooi adds is the rest of the story. Stack a workspace on another workspace's branch, and when the parent PR merges, Wooi retargets each child PR's base to the grandparent branch and rebases the children onto it, so the rest of the chain stays valid instead of quietly rotting. A stack you built by hand with git checkout -b and gh pr create gets picked up too, reconstructed from the PRs' base branches. And reviewing someone else's PR is its own row in the sidebar with its own worktree — three panes, comments batched and posted to GitHub as real review comments. 출발점은 다른 도구들과 같다. 작업마다 worktree 하나, 브랜치 하나, 에이전트 하나가 병렬로 돈다. Wooi 가 더하는 건 그 다음 이야기다. 워크스페이스를 다른 워크스페이스의 브랜치 위에 스택으로 얹고, 부모 PR 이 머지되면 Wooi 가 각 자식 PR 의 base 를 조부모 브랜치로 다시 잡고 자식들을 그 위로 rebase 한다. 나머지 체인이 조용히 썩는 대신 멀쩡하게 남는다. git checkout -b 와 gh pr create 로 직접 쌓은 스택도 PR 의 base 브랜치를 읽어 복원한다. 남의 PR 리뷰는 사이드바에서 자기 줄과 자기 worktree 를 갖는다. 세 개의 패널, 모아서 보내는 코멘트, GitHub 에 실제 리뷰 코멘트로 게시.

Is Wooi the right pick? Wooi 가 맞는 선택일까

Worth being honest about, because for plenty of workflows the answer is no. 솔직하게 적어 둔다. 적지 않은 경우에 답은 "아니오"다.

Pick Wooi whenWooi 가 맞을 때

  • Your work naturally comes in chains — schema, then API, then UI — and you are tired of rebasing them by hand in order. 작업이 자연스럽게 사슬로 온다. 스키마 다음 API 다음 UI. 그걸 매번 순서대로 손으로 rebase 하는 데 질렸다.
  • You already open stacked PRs and want the merge cascade handled for you. 이미 스택 PR 을 열고 있고, 머지 캐스케이드를 도구가 처리해 주길 원한다.
  • Reviewing other people's PRs is a real part of your day, not an afterthought. 남의 PR 리뷰가 하루 일과의 실제 일부다. 곁다리가 아니다.
  • You are on a Mac, using Claude Code or Codex. 맥을 쓰고, Claude Code 나 Codex 를 쓴다.

Pick something else when다른 게 맞을 때

  • You are on Windows or Linux — Wooi is macOS only. Emdash and Orca are cross-platform; Claude Squad runs anywhere tmux does. Windows 나 Linux 를 쓴다. Wooi 는 macOS 전용이다. Emdash 와 Orca 는 크로스 플랫폼이고, Claude Squad 는 tmux 가 도는 곳이면 어디서든 돈다.
  • Your tasks are genuinely independent. Then stacking is machinery you will never touch, and a lighter tool will feel better. 작업들이 정말로 서로 독립적이다. 그러면 스태킹은 평생 안 건드릴 장치고, 더 가벼운 도구가 낫다.
  • You want to run agents on remote machines over SSH, or from your phone. Emdash and Orca do that; Wooi does not. SSH 로 원격 머신에서, 또는 휴대폰에서 에이전트를 돌리고 싶다. Emdash 와 Orca 가 그걸 한다. Wooi 는 안 한다.
  • You need a planning board and ticket sync more than you need branch plumbing. 브랜치 배관보다 계획 보드와 티켓 연동이 더 급하다.
